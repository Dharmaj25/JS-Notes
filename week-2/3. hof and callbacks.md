# Higher-Order Functions + Callbacks

---

## What is a Higher-Order Function?

You already know functions are first-class — they can be passed around like values.
A Higher-Order Function simply uses that fact.

> **A higher-order function is any function that:**
> - Takes a function as an argument, OR
> - Returns a function, OR
> - Both

That's the complete definition.

```js
// Takes a function → HOF
function runTwice(fn) {
  fn();
  fn();
}

// Returns a function → HOF
function multiplier(x) {
  return function(y) {
    return x * y;
  };
}

const triple = multiplier(3);
triple(5); // 15

// Both → HOF
function pipe(fn1, fn2) {
  return function(value) {
    return fn2(fn1(value));
  };
}

const doubleThenAddOne = pipe(
  n => n * 2,
  n => n + 1
);

doubleThenAddOne(5); // 11
```

---

## Why HOFs Exist — The Real Reason

Without HOFs, you repeat the same structure with only the operation changing:

```js
// Without HOF — repetitive structure
function doubleArray(arr) {
  const result = [];
  for (let i = 0; i < arr.length; i++) {
    result.push(arr[i] * 2);
  }
  return result;
}

function squareArray(arr) {
  const result = [];
  for (let i = 0; i < arr.length; i++) {
    result.push(arr[i] * arr[i]);
  }
  return result;
}
```

The loop structure is identical. Only the operation changes.
HOFs let you extract the structure and inject the operation:

```js
// With HOF — one function, infinite behaviors
function transformArray(arr, fn) {
  const result = [];
  for (let i = 0; i < arr.length; i++) {
    result.push(fn(arr[i]));
  }
  return result;
}

transformArray([1, 2, 3], n => n * 2);   // [2, 4, 6]
transformArray([1, 2, 3], n => n * n);   // [1, 4, 9]
transformArray([1, 2, 3], n => n + 10);  // [11, 12, 13]
```

This is exactly how `map`, `filter`, `reduce` work under the hood.
You will implement them from scratch in Week 3.

## What is a Callback?

A callback is a function passed to another function to be called later.

```js
function greet(name, callback) {
  const message = "Hello " + name;
  callback(message); // calling the passed function
}

greet("Alice", function(msg) {
  console.log(msg); // "Hello Alice"
});
```

`greet` is the HOF. The anonymous function is the callback.
The callback is just a function being passed as a value — first-class functions making this possible.

---

## Synchronous Callbacks

Called immediately, inline, during the current execution.
Nothing is delayed. Everything runs in order.

```js
function transformArray(arr, fn) {
  const result = [];
  for (let i = 0; i < arr.length; i++) {
    result.push(fn(arr[i])); // fn called right here, right now
  }
  return result;
}

const doubled = transformArray([1, 2, 3], n => n * 2);
console.log(doubled); // [2, 4, 6]
console.log("done");
```

Execution order:
```
transformArray called
  → fn(1) → 2
  → fn(2) → 4
  → fn(3) → 6
doubled = [2, 4, 6]
console.log("done")
```

Completely predictable. Runs top to bottom.

More sync callback examples:
```js
[1, 2, 3].map(n => n * 2);        // callback called synchronously
[1, 2, 3].filter(n => n > 1);     // callback called synchronously
[1, 2, 3].sort((a, b) => a - b);  // callback called synchronously
```

---

## Asynchronous Callbacks

Called LATER — not immediately.
The current code keeps running, and the callback fires at some point in the future when an event or operation completes.

```js
console.log("before");

setTimeout(function() {
  console.log("inside timeout");
}, 1000);

console.log("after");
```

Output:
```
"before"
"after"
"inside timeout"  ← runs 1 second later
```

`"after"` prints before `"inside timeout"` even though `setTimeout` appears first in the code.
JS does not wait for it — it keeps running and comes back to the callback later.

More async callback examples:
```js
// Event listener — fires when user clicks in the future
document.addEventListener("click", function() {
  console.log("clicked");
});

// Network request — fires when response arrives
fetch("https://api.example.com")
  .then(function(response) {
    console.log(response); // fires in the future
  });
```

---

## Sync vs Async — The Core Difference

```
SYNC callback:
  → Called immediately during the current function execution
  → Execution waits for it to finish
  → Predictable, top-to-bottom order

ASYNC callback:
  → Called later, after some operation completes
  → Execution does NOT wait for it
  → Order depends on when the operation finishes
```

---

## How JS Handles Async — The Basic Mental Model

JS is **single-threaded** — it can only do one thing at a time.

When you call `setTimeout(fn, 1000)`:

```
Step 1: JS hands the timer to the browser's Web API
Step 2: JS keeps running — does NOT wait
Step 3: 1 second passes (browser handles this)
Step 4: Browser puts fn in the callback queue
Step 5: When JS finishes what it's doing, it picks fn
        from the queue and runs it
```

This is why async callbacks never interrupt the currently running code.
The full event loop mechanism is covered in Week 4 — Async JavaScript.

## Callback Hell — The Real Problem

Callbacks are powerful. But when you chain multiple async operations where each depends on the result of the previous one, you get **callback hell** — also called the **pyramid of doom**.

### The Scenario

Fetch a user → then fetch their orders → then fetch order details → then send a notification:

```js
getUser(userId, function(user) {
  getOrders(user.id, function(orders) {
    getOrderDetails(orders[0].id, function(details) {
      sendNotification(details, function(result) {
        console.log("done");
      });
    });
  });
});
```

Each level needs the result of the previous one.
So you nest callbacks inside callbacks inside callbacks.
Code grows rightward — the pyramid of doom.

With real-world error handling it gets worse:

```js
getUser(userId, function(err, user) {
  if (err) { handleError(err); return; }

  getOrders(user.id, function(err, orders) {
    if (err) { handleError(err); return; }

    getOrderDetails(orders[0].id, function(err, details) {
      if (err) { handleError(err); return; }

      sendNotification(details, function(err, result) {
        if (err) { handleError(err); return; }
        console.log("done");
      });
    });
  });
});
```

---

## Why Callback Hell is a Problem

**1. Readability**
Code grows rightward — the pyramid of doom.
Deeply nested code is extremely hard to read and follow.

**2. Error handling**
You must handle errors at every single level separately.
Miss one level and errors silently swallow themselves.

**3. Inversion of control**
This is the deepest problem.

When you pass a callback to a function — especially a third-party one:

```js
thirdPartyLibrary.doSomething(myCallback);
```

You've handed `myCallback` to someone else.
You've lost control of:
- **When** it gets called
- **How many times** it gets called
- **Whether** it gets called at all
- **What arguments** it receives

You're trusting the library completely. This is **inversion of control** — your own function's execution is now in someone else's hands.

```js
// What if the library does this?
function doSomething(callback) {
  callback(); // called once
  callback(); // called again — you didn't expect this
}

// Or this?
function doSomething(callback) {
  // callback never called
  // your code silently stops here, you never know why
}
```

**4. Debugging**
Stack traces in nested callbacks are messy.
Hard to pinpoint exactly where something went wrong.

---

## Inversion of Control — Why Promises Were Invented

Promises were invented specifically to solve inversion of control.

Instead of giving your function away:
```js
// Callback — you hand control away
thirdParty.doSomething(myCallback);
```

Promises give you back a value you control:
```js
// Promise — you stay in control
const promise = thirdParty.doSomething();
promise.then(myCallback);
```

With a Promise, YOU decide what to do with the result.
The library gives you a value — not control over your function.

Promises are covered fully in Week 4. For now, understand this:

> **Callback hell is not just about ugly nesting. The real problem is inversion of control — losing ownership of when and how your code runs.**

## Built-in HOFs You Use Every Day

These are all higher-order functions — they all take a function as an argument:

```js
// map — transforms every element
[1, 2, 3].map(n => n * 2);           // [2, 4, 6]

// filter — keeps elements that pass the test
[1, 2, 3, 4].filter(n => n > 2);     // [3, 4]

// reduce — reduces to a single value
[1, 2, 3].reduce((acc, n) => acc + n, 0); // 6

// sort — sorts by comparator
[3, 1, 2].sort((a, b) => a - b);     // [1, 2, 3]

// setTimeout — calls fn after delay
setTimeout(() => console.log("hi"), 1000);

// addEventListener — calls fn on event
document.addEventListener("click", () => console.log("clicked"));
```

All of these are HOFs. All of them take your function and call it at some point — some synchronously, some asynchronously.

## Functions Returning Functions — The HOF Pattern

This pattern appears constantly in JS — closures, currying, middleware, decorators all use it.

```js
// A function that creates a greeting function
function makeGreeter(greeting) {
  return function(name) {
    return greeting + " " + name;
  };
}

const sayHello = makeGreeter("Hello");
const sayHi    = makeGreeter("Hi");

sayHello("Alice"); // "Hello Alice"
sayHi("Bob");      // "Hi Bob"
```

`makeGreeter` returns a different function each time — customized by the argument.
This is a HOF returning a function.

```js
// A function that wraps another function with logging
function withLogging(fn) {
  return function(x) {
    console.log("Calling with", x);
    const result = fn(x);
    console.log("Result:", result);
    return result;
  };
}

const double = n => n * 2;
const loggedDouble = withLogging(double);

loggedDouble(5);
// "Calling with 5"
// "Result: 10"
```

`withLogging` takes a function AND returns a function — classic HOF doing both.
This pattern is called a **decorator** — wrapping a function to add behavior without changing its core logic.

---

## How Everything Connects

```
First-class functions
  → functions are values
  → you can pass them, return them, store them

Higher-order functions
  → take functions as arguments or return them
  → built on first-class functions

Callbacks
  → functions passed to HOFs to be called later
  → sync: called immediately (map, filter, sort)
  → async: called later (setTimeout, event listeners, fetch)

Callback hell
  → deeply nested async callbacks
  → real problem: inversion of control
  → solution: Promises (Week 4)
```

**Q10 — HOF chaining**
```js
function compose(fn1, fn2) {
  return function(value) {
    return fn1(fn2(value));
  };
}

const addOne  = n => n + 1;
const double  = n => n * 2;

const doubleFirst  = compose(addOne, double);
const addOneFirst  = compose(double, addOne);

console.log(doubleFirst(5));
console.log(addOneFirst(5));
```
<details>
<summary>Answer</summary>

`11` — `doubleFirst(5)`: `fn2` runs first → `double(5) = 10`, then `fn1` → `addOne(10) = 11`.
`12` — `addOneFirst(5)`: `fn2` runs first → `addOne(5) = 6`, then `fn1` → `double(6) = 12`.

In `compose`, the RIGHT function runs first, then the LEFT.
Note: `pipe` is the opposite — left runs first, then right.
</details>

**Q14 — Identifying HOF type**
```js
// Which of these are HOFs and why?

function a(x) { return x + 1; }

function b(fn) { return fn(5); }

function c(x) { return function(y) { return x + y; }; }

function d(fn, x) { return fn(x) * 2; }

```
<details>
<summary>Answer</summary>

`a` — NOT a HOF. Takes a number, returns a number. No functions involved.
`b` — HOF. Takes a function `fn` as argument.
`c` — HOF. Returns a function.
`d` — HOF. Takes a function `fn` as argument.
`e` — NOT a HOF. Takes two numbers, returns a number. No functions involved.
</details>

**Q15 — The callback timing trap**
```js
let result = 0;

setTimeout(function() {
  result = 42;
}, 0);

console.log(result);
```
<details>
<summary>Answer</summary>

`0` — not `42`.
The `setTimeout` callback runs asynchronously — after the current execution finishes.
`console.log(result)` runs before the callback fires, so `result` is still `0`.
This is one of the most common async mistakes beginners make — expecting an async callback to run before the next line.
</details>

**Q16 — Custom HOF with condition**
```js
function filterArray(arr, fn) {
  const result = [];
  for (let i = 0; i < arr.length; i++) {
    if (fn(arr[i])) {
      result.push(arr[i]);
    }
  }
  return result;
}

const numbers = [1, 2, 3, 4, 5, 6];

console.log(filterArray(numbers, n => n % 2 === 0));
console.log(filterArray(numbers, n => n > 3));
console.log(filterArray(numbers, n => n === 1 || n === 6));
```
<details>
<summary>Answer</summary>

`[2, 4, 6]` — even numbers only.
`[4, 5, 6]` — numbers greater than 3.
`[1, 6]` — only 1 or 6.
This is exactly how `Array.prototype.filter` works internally. You'll implement the polyfill in Week 5.
</details>

## What Interviewers Test

**1. Define HOF correctly**
Takes a function as argument OR returns a function OR both. Simple definition — but you must be precise.

**2. Difference between sync and async callbacks**
Sync → runs immediately, execution waits. Async → runs later, execution doesn't wait. Know the order of output for both.

**3. Explain callback hell**
Not just "deeply nested code". Explain inversion of control — you've handed control of your function to someone else. That's the real problem.

**4. Why Promises were invented**
To solve inversion of control. With promises, you get back a value you can work with — you're no longer handing your function away.

**5. Identify HOFs in code**
Given a function, be able to say yes or no and explain why.

**6. The async timing trap**
Code after `setTimeout` runs before the callback — even with 0 delay. This is a very common output question.

**7. Functions returning functions**
Be comfortable reading and tracing HOFs that return functions. This is the foundation for closures (tomorrow), currying, and composition.

## Mental Models

**HOF = a function that works with other functions.**
Either it takes one in, or gives one out. That's it.

**Callback = "here's a function, call it when you're ready."**
You're passing a function as a value. The receiver decides when to call it.

**Sync callback = you hand someone a hammer and they use it immediately.**
Right now. In front of you. You wait.

**Async callback = you hand someone a hammer and they'll use it later.**
They put it aside. You walk away. They use it when the time is right.

**Callback hell = you've lost control of your own code.**
Nesting is the symptom. Inversion of control is the disease. Promises are the cure.
