## Section 1 — Conceptual Questions (The Whats)

These are the "explain this to me" questions. Answer in 2-4 sentences max. Crisp and clear.

---

**1.1** What is the difference between a primitive and a reference type in JavaScript?

<details>
<summary>Answer</summary>

Primitives are stored by value on the stack — copying creates an independent copy. Reference types are stored on the heap, and the variable holds a memory address pointing to the data. Copying copies the address — both variables point to the same object.
</details>

---

**1.2** What are the 7 primitive types in JavaScript?

<details>
<summary>Answer</summary>

`string`, `number`, `boolean`, `null`, `undefined`, `symbol`, `bigint`
</details>

---

**1.3** What is the difference between `==` and `===`?

<details>
<summary>Answer</summary>

`===` (strict equality) checks value AND type — no coercion happens. `==` (loose equality) coerces types before comparing. Always prefer `===` unless you specifically want `null == undefined` to be true.
</details>

---

**1.4** What is type coercion in JavaScript?

<details>
<summary>Answer</summary>

Type coercion is JS automatically converting one type to another to complete an operation. Implicit coercion happens without you asking (`"5" - 1 = 4`). Explicit coercion is when you do it yourself (`Number("5")`).
</details>

---

**1.5** What is the Temporal Dead Zone (TDZ)?

<details>
<summary>Answer</summary>

TDZ is the period between when a `let`/`const` variable is hoisted (creation phase) and when its declaration line is executed. Accessing the variable in this window throws `ReferenceError: Cannot access before initialization`.
</details>

---

**1.6** What is hoisting?

<details>
<summary>Answer</summary>

Hoisting is JS allocating memory for all declarations before running code — it happens during the creation phase of the execution context. `var` is hoisted and initialized to `undefined`. `let`/`const` are hoisted but placed in TDZ. Function declarations are fully hoisted with their body.
</details>

---

**1.7** What is scope in JavaScript?

<details>
<summary>Answer</summary>

Scope is the area of code where a variable exists and can be accessed. JS has three types: global scope (everywhere), function scope (inside a function only), and block scope (inside `{}` — only `let`/`const`).
</details>

---

**1.8** What is the scope chain?

<details>
<summary>Answer</summary>

When JS looks up a variable, it starts in the current scope and walks outward — one scope at a time — until it finds the variable or reaches global scope and throws a ReferenceError. It never searches inward. This chain of scopes is the scope chain.
</details>

---

**1.9** What is lexical scope?

<details>
<summary>Answer</summary>

Lexical scope means a function's scope is determined by where it is written in the code — not where it is called from. The scope chain is fixed at definition time and never changes regardless of how or where the function is called.
</details>

---

**1.10** What is an Execution Context?

<details>
<summary>Answer</summary>

An Execution Context is a box JS creates every time it runs code. It contains a Variable Environment (var declarations), a Lexical Environment (let/const + outer reference), and the value of `this`. It runs in two phases: creation (hoisting) then execution (code runs line by line).
</details>

---

**1.11** What is the Call Stack?

<details>
<summary>Answer</summary>

The Call Stack is a LIFO (last in, first out) data structure JS uses to track execution contexts. The GEC sits at the bottom. Every function call pushes a new EC on top. When a function returns, its EC is popped. Whatever is on top is currently executing. JS is single-threaded — only one EC runs at a time.
</details>

---

**1.12** What is Garbage Collection in JavaScript?

<details>
<summary>Answer</summary>

Garbage Collection is JS's automatic memory management system. It uses a Mark and Sweep algorithm — starting from roots (global variables + current call stack), it marks all reachable objects as alive, then sweeps (frees) everything not marked. If something is unreachable from any root, it gets collected.
</details>

---

**1.13** What is a memory leak in JavaScript?

<details>
<summary>Answer</summary>

A memory leak is memory you no longer need but JS can't free because something still holds a reference to it. GC can't collect it since it's still technically reachable. Over time, leaks cause the app to slow down, consume more RAM, and eventually crash.
</details>

---

**1.14** What is the difference between the Variable Environment and the Lexical Environment?

<details>
<summary>Answer</summary>

At global scope they point to the same object. Inside functions/blocks they differ — `var` goes into the Variable Environment (function-scoped), `let`/`const` go into the Lexical Environment (block-scoped). The Lexical Environment also holds the outer reference that enables the scope chain.
</details>

---

**1.15** What is autoboxing in JavaScript?

<details>
<summary>Answer</summary>

When you call a method on a primitive (e.g. `"hello".toUpperCase()`), JS temporarily wraps it in its object wrapper (`String`, `Number`, `Boolean`), calls the method, then discards the wrapper. This is autoboxing — it's why primitives appear to have methods despite being value types.
</details>

## Section 2 — The Hows

These are "how does X work" questions. They go one level deeper than the whats.

---

**2.1** How does JS decide what `var`, `let`, and `const` do at runtime?

<details>
<summary>Answer</summary>

During the creation phase of the execution context, JS scans all declarations. `var` gets allocated and set to `undefined`. `let`/`const` get allocated but locked in TDZ. Then during the execution phase, code runs line by line — assignments happen, and `let`/`const` exit TDZ when their declaration line is reached.
</details>

---

**2.2** How does the scope chain actually work under the hood?

<details>
<summary>Answer</summary>

Each Lexical Environment has two parts: an Environment Record (stores variables) and an Outer Reference (points to the parent Lexical Environment). When JS looks up a variable, it checks the current Environment Record — not found? Follow the outer reference. Keep following until found or null (global). This linked list of environments IS the scope chain.
</details>

---

**2.3** How does `==` coerce types? Walk through the rules.

<details>
<summary>Answer</summary>

In order: (1) Same type → compare directly. (2) `null == undefined` → always true, nothing else. (3) Either NaN → always false. (4) Boolean vs anything → convert boolean to number first, then restart. (5) String vs number → convert string to number. (6) Object vs primitive → convert object to primitive via `.valueOf()`/`.toString()`, restart.
</details>

---

**2.4** How does Mark and Sweep garbage collection work?

<details>
<summary>Answer</summary>

Step 1 (Mark): Start from all roots (global variables, current call stack). Follow every reference. Mark every reachable object as alive. Step 2 (Sweep): Go through all heap memory. Everything not marked gets freed. This runs periodically in the background — you never call it manually.
</details>

---

**2.5** How does `const` work with objects? Why can you mutate but not reassign?

<details>
<summary>Answer</summary>

`const` locks the variable binding — the memory address stored in the variable cannot change. But the object at that address can still be modified. Mutation (`obj.x = 1`) changes what's inside the address. Reassignment (`obj = {}`) tries to change the address itself — that's what `const` prevents.
</details>

---

**2.6** How does the `for` loop `var` vs `let` closure bug actually work?

<details>
<summary>Answer</summary>

With `var`, there's ONE shared `i` in the enclosing scope. All callbacks close over the same variable. By the time they fire, the loop is done and `i = 3`. With `let`, JS creates a new `i` binding per iteration — each callback closes over its own copy of `i` at that moment.
</details>

---

**2.7** How does variable shadowing work? Does it update the outer variable?

<details>
<summary>Answer</summary>

No. Shadowing creates a brand new variable in the inner scope with the same name. It hides (shadows) the outer one — but the outer variable is completely unaffected. The inner variable and outer variable are two separate entries in two separate Environment Records.
</details>

---

**2.8** How does JS determine what's "reachable" for garbage collection?

<details>
<summary>Answer</summary>

JS starts from roots — global variables and variables in functions currently on the call stack. From these roots, it follows every reference it can find. Anything reachable through this traversal = alive. Anything NOT reachable from any root = garbage, eligible for collection.
</details>

---

**2.9** How is `null` different from `undefined`?

<details>
<summary>Answer</summary>

`undefined` means a variable has been declared but not yet assigned a value — it's the default. `null` is an intentional assignment meaning "no value" — a developer explicitly set it. `typeof undefined` = `"undefined"`. `typeof null` = `"object"` (legacy bug). `null == undefined` is `true`, but `null === undefined` is `false`.
</details>

---

**2.10** How does JS handle memory for primitives vs objects?

<details>
<summary>Answer</summary>

Primitives are stored directly on the stack — fast, limited, automatically cleaned when the EC is popped. Objects are stored on the heap — larger, flexible, but require garbage collection when no longer referenced. The stack holds a variable that either contains the value (primitive) or holds the address of the heap object (reference type).
</details>

## Section 3 — The Whys

These are "why does X work this way" questions. Shows deeper understanding.

---

**3.1** Why does `typeof null` return `"object"`?

<details>
<summary>Answer</summary>

It's a legacy bug from JavaScript's first version. In the original implementation, values were stored with a type tag — null had the same tag as objects (000). The bug was never fixed to avoid breaking existing code on the web.
</details>

---

**3.2** Why does `let`/`const` have TDZ but `var` doesn't?

<details>
<summary>Answer</summary>

TDZ was intentionally introduced with `let`/`const` to make bugs loud and immediate. `var`'s silent `undefined` before assignment hides bugs — you access a variable that appears to exist but gives a meaningless value. TDZ throws a ReferenceError immediately, exactly at the problem line, making it easy to find and fix.
</details>

---

**3.3** Why can't you use `var` inside a block and expect it to stay there?

<details>
<summary>Answer</summary>

Because `var` was designed before block scope existed in JS. It only respects function boundaries — not `if`, `for`, `while`, or standalone `{}` blocks. Those boundaries are invisible to `var`. This was a design decision that `let`/`const` later fixed.
</details>

---

**3.4** Why does JS use lexical scope instead of dynamic scope?

<details>
<summary>Answer</summary>

Lexical scope (scope set at write time) makes code predictable — you can look at where a function is written and know exactly what variables it can access. Dynamic scope (scope set at call time) would make this unpredictable — the same function could access different variables depending on where it's called from. Lexical scope also enables closures.
</details>

---

**3.5** Why does reassigning a function parameter not affect the original object?

<details>
<summary>Answer</summary>

Because JS passes a copy of the reference — not the reference itself. Mutation (`obj.x = 1`) follows the copied address to the same heap object and modifies it. Reassignment (`obj = {}`) only changes what the local copy of the address points to — the caller's original address variable is untouched.
</details>

---

**3.6** Why does `var` at global scope attach to `window` but `let`/`const` don't?

<details>
<summary>Answer</summary>

At global scope, `var` goes into the Variable Environment which IS the global object (`window` in browsers). `let`/`const` go into a separate Lexical Environment that is NOT the global object. This was a design improvement — polluting `window` causes silent bugs when you accidentally override browser built-ins like `window.top` or `window.name`.
</details>

---

**3.7** Why is `NaN` not equal to itself?

<details>
<summary>Answer</summary>

`NaN` stands for "Not a Number" and represents the result of an invalid mathematical operation. IEEE 754 (the floating point standard JS uses) specifies that NaN is never equal to anything — including itself — because any two invalid operations could produce different kinds of "not a number". Use `Number.isNaN(x)` to check for NaN.
</details>

---

**3.8** Why does the for loop bug happen and why does `let` fix it?

<details>
<summary>Answer</summary>

With `var`, there's a single `i` shared across all iterations — callbacks close over the same variable, and by the time they run the loop has finished. With `let`, JS creates a new binding per iteration — each callback closes over its own independent `i`. The fix works because `let` is block-scoped to each loop iteration's block.
</details>

---

**3.9** Why does `Object.freeze()` only provide shallow immutability?

<details>
<summary>Answer</summary>

`Object.freeze()` prevents adding, modifying, or removing properties on the frozen object itself. But nested objects are separate objects in memory — `freeze` only freezes the reference to them, not the objects themselves. Those nested objects remain mutable. For deep immutability you need to recursively freeze every nested object.
</details>

---

**3.10** Why do function declarations get fully hoisted but function expressions don't?

<details>
<summary>Answer</summary>

Function declarations are a distinct syntax that JS treats specially — the engine stores the entire function during the creation phase so it's available anywhere in its scope. Function expressions are just variable assignments — only the variable declaration is hoisted (as `undefined` for `var`, or TDZ for `let`/`const`). The function body is just a value being assigned and that happens at execution time.
</details>

## Section 5 — Tricky Questions

These are designed to catch you off guard. Ones that even experienced devs get wrong.

---

**5.1**
```js
console.log(typeof typeof 42);
```
<details>
<summary>Answer</summary>

`"string"`. `typeof 42` = `"number"` (a string). `typeof "number"` = `"string"`. `typeof` always returns a string.
</details>

---

**5.2**
```js
var a = b = 5;
console.log(typeof a);
console.log(typeof b);
```
<details>
<summary>Answer</summary>

Both `"number"`. But `b` is an accidental global — `b = 5` without `var`/`let`/`const` puts it on `window`. `var a = (b = 5)` — `b` assigned first (global), then `a` declared as var with value 5.
</details>

---

**5.3**
```js
(function() {
  var a = b = 5;
})();
console.log(typeof a);
console.log(typeof b);
```
<details>
<summary>Answer</summary>

`"undefined"` for `a` — `var a` is function-scoped, not accessible outside.  
`"number"` for `b` — `b` is a global (no declaration keyword), accessible outside the IIFE.
</details>

---

**5.4**
```js
console.log(0.1 + 0.2 === 0.3);
```
<details>
<summary>Answer</summary>

`false`. Floating point precision issue — `0.1 + 0.2` = `0.30000000000000004`. Use `Math.abs((0.1 + 0.2) - 0.3) < Number.EPSILON` to compare floats.
</details>

---

**5.5**
```js
console.log([] + []);
console.log([] + {});
console.log({} + []);
```
<details>
<summary>Answer</summary>

`""` — `[]` → `""`, `"" + ""` = `""`.  
`"[object Object]"` — `[]` → `""`, `{}` → `"[object Object]"`, concatenated.  
`0` — when `{}` is at the start of a line, JS treats it as an empty block (not an object). So it's `+[]` which is `+""` = `0`. (In some contexts returns `"[object Object]"` — depends on environment).
</details>

---

**5.6**
```js
var x = 10;
function foo() {
  console.log(x);
  var x = 20;
  console.log(x);
}
foo();
console.log(x);
```
<details>
<summary>Answer</summary>

`undefined` — `var x` inside `foo` is hoisted, shadows global `x`, is `undefined` at first log.  
`20` — assigned now.  
`10` — global `x` untouched.
</details>

---

**5.7**
```js
console.log(+"");
console.log(+null);
console.log(+undefined);
console.log(+false);
console.log(+[]);
console.log(+{});
```
<details>
<summary>Answer</summary>

`0`, `0`, `NaN`, `0`, `0`, `NaN`.  
Unary `+` converts to number. `""` → `0`, `null` → `0`, `undefined` → `NaN`, `false` → `0`, `[]` → `""` → `0`, `{}` → `"[object Object]"` → `NaN`.
</details>

---

**5.8**
```js
let a = { x: 1 };
let b = { x: 1 };
let c = a;

console.log(a == b);
console.log(a === b);
console.log(a === c);
```
<details>
<summary>Answer</summary>

`false` — different objects in memory.  
`false` — same check, same result.  
`true` — `c` is assigned `a`'s reference. They point to the same object.
</details>

---

**5.9**
```js
const obj = { a: 1 };
const copy = obj;
copy.a = 999;
const frozen = Object.freeze({ b: 1 });
frozen.b = 999;

console.log(obj.a);
console.log(frozen.b);
```
<details>
<summary>Answer</summary>

`999` — `copy` and `obj` share the same reference. Mutation visible through both.  
`1` — `freeze` prevents mutation. Silently fails (throws in strict mode).
</details>

---

**5.10**
```js
function foo() {
  return
  {
    name: "Alice"
  };
}
console.log(foo());
```
<details>
<summary>Answer</summary>

`undefined`. Automatic Semicolon Insertion (ASI) — JS inserts a semicolon after `return` because there's a newline. The object is never reached. Always put `{` on the same line as `return`.
</details>

---

**5.11**
```js
let a;
console.log(a == null);
console.log(a === null);
console.log(a === undefined);
```
<details>
<summary>Answer</summary>

`true` — `a` is `undefined`. `undefined == null` is the special pair — true.  
`false` — `undefined !== null` strictly.  
`true` — `a` is `undefined` since it was declared but not assigned.
</details>

---

**5.12**
```js
console.log(Boolean("false"));
console.log(Boolean("0"));
console.log(Boolean([]));
console.log(Boolean({}));
console.log(Boolean(""));
console.log(Boolean(0));
```
<details>
<summary>Answer</summary>

`true` — non-empty string.  
`true` — non-empty string (not the number 0).  
`true` — arrays are always truthy, even empty ones.  
`true` — objects are always truthy, even empty ones.  
`false` — empty string is falsy.  
`false` — `0` is falsy.
</details>

**5.13 — The creation phase priority question**
```js
console.log(foo);
var foo = "variable";
function foo() { return "function"; }
console.log(foo);
```
<details>
<summary>Answer</summary>

`ƒ foo() { return "function"; }` — function declaration wins hoisting priority over var.  
`"variable"` — execution reassigns `foo` to the string.
</details>

**5.14**
```js
for (var i = 0; i < 3; i++) {
  (function(j) {
    setTimeout(() => console.log(j), 0);
  })(i);
}
```
<details>
<summary>Answer</summary>

`0, 1, 2`. The IIFE creates a new function scope per iteration. `j` gets a copy of `i` at that moment. This is the old fix before `let` existed.
</details>

**5.15**
```js
function outer() {
  var x = 10;
  return function inner() {
    console.log(x);
  };
}
const fn = outer();
fn();
```
<details>
<summary>Answer</summary>

`10`. Preview of closures — `inner` carries its lexical environment (outer's scope) with it. Even after `outer` returns and its EC is popped, `x` stays alive because `inner` still references it.
</details>

## Section 6 — Follow-up Questions

These are what interviewers ask after your initial answer. Be ready for these specifically.

---

**6.1** After explaining hoisting → *"Are `let` and `const` hoisted?"*

<details>
<summary>Answer</summary>

Yes — both are hoisted. The proof: the error says "Cannot access before initialization" not "is not defined". If they weren't hoisted, JS wouldn't know they exist. They're hoisted but placed in TDZ instead of being initialized. The inner block TDZ shadowing example proves it — the inner `let` shadows the outer variable even before its declaration line.
</details>

---

**6.2** After explaining `const` → *"How do you make an object truly immutable?"*

<details>
<summary>Answer</summary>

`Object.freeze()` for shallow immutability — prevents adding, modifying, or deleting properties on the object itself. But nested objects are not frozen. For deep immutability, recursively freeze every nested object, or use an immutability library like Immer.
</details>

---

**6.3** After explaining scope chain → *"What is the difference between scope chain and prototype chain?"*

<details>
<summary>Answer</summary>

Scope chain = how JS finds variables. It walks up lexical environments (where code was written). Prototype chain = how JS finds properties on objects. It walks up the `__proto__` links. Scope chain is about variable lookup. Prototype chain is about property lookup on objects.
</details>

---

**6.4** After explaining GC → *"How would you detect a memory leak in a real application?"*

<details>
<summary>Answer</summary>

Chrome DevTools — Performance tab: record while using the app and watch the memory graph. If it keeps climbing without dropping, there's a leak. Memory tab: take heap snapshots at different points and compare — objects that keep growing are leak candidates. Signs: app slowing over time, browser tab consuming more RAM, eventual crash.
</details>

---

**6.5** After explaining `==` rules → *"When is it okay to use `==` instead of `===`?"*

<details>
<summary>Answer</summary>

One legitimate use case: `value == null` — this catches both `null` and `undefined` in one check, which is cleaner than `value === null || value === undefined`. That's about it. Everywhere else, use `===`.
</details>

---

**6.6** After explaining `var` → *"Why would anyone still use `var` today?"*

<details>
<summary>Answer</summary>

Realistically — they wouldn't in new code. `var` exists today only for backward compatibility with old codebases. In modern JS, `const` by default, `let` when reassignment is needed, `var` never.
</details>

---

**6.7** After explaining primitives are passed by value → *"Is JavaScript pass-by-value or pass-by-reference?"*

<details>
<summary>Answer</summary>

Always pass-by-value. For primitives — the value itself is copied. For objects — a copy of the memory address (reference) is passed. This is sometimes called "pass by value of the reference" or "pass by sharing". True pass-by-reference would mean reassigning the parameter inside the function affects the original — JS never does that.
</details>

---

**6.8** After explaining execution context → *"What is the difference between GEC and FEC?"*

<details>
<summary>Answer</summary>

GEC (Global Execution Context) is created once when the script loads. It represents everything outside all functions. `this` = `window`/`global`. FEC (Function Execution Context) is created every time a function is called — each call creates a fresh one. Both run the same two phases (creation + execution).
</details>

---

**6.9** After explaining the for loop `var` bug → *"How would you fix it without using `let`?"*

<details>
<summary>Answer</summary>

Use an IIFE (Immediately Invoked Function Expression) to create a new scope per iteration: `for (var i = 0; i < 3; i++) { (function(j) { setTimeout(() => console.log(j), 0); })(i); }`. Each IIFE call creates its own function scope with its own `j` — captures the current value of `i`.
</details>

---

**6.10** After explaining lexical scope → *"How does lexical scope enable closures?"*

<details>
<summary>Answer</summary>

A function's scope chain is determined by where it's written — and that scope chain is carried with the function wherever it goes. If an inner function is returned and the outer function's EC is popped, the inner function still holds a reference to the outer Lexical Environment. That environment stays alive in memory. This is a closure — the function remembers the scope it was created in.
</details>

## Section 7 — Concept Connection Questions

These test whether you can connect dots between topics — what SDE2 actually requires.

---

**7.1** How does hoisting connect to execution context?

<details>
<summary>Answer</summary>

Hoisting IS the creation phase of the execution context. Before code runs, JS creates an EC and scans all declarations — var gets undefined, let/const get TDZ, function declarations get fully stored. This is what we call hoisting. They're the same mechanism described from two different angles.
</details>

---

**7.2** How does scope connect to lexical environment?

<details>
<summary>Answer</summary>

Scope is the concept. Lexical Environment is the implementation. Each scope in JS is represented by a Lexical Environment (an Environment Record + Outer Reference). The scope chain is literally a linked list of Lexical Environments connected by their outer references.
</details>

---

**7.3** How does garbage collection connect to closures?

<details>
<summary>Answer</summary>

Normally when a function returns, its EC is popped and variables become unreachable — GC collects them. But if an inner function (closure) is returned and still referenced, it holds an outer reference to the outer function's Lexical Environment — keeping it reachable. GC won't collect those variables. This is how closures keep outer variables alive beyond the outer function's lifetime.
</details>

---

**7.4** How does TDZ connect to block scope?

<details>
<summary>Answer</summary>

When a block starts, all `let`/`const` in it are hoisted to the top of that block's Lexical Environment and placed in TDZ. TDZ applies per block — each block creates a new Lexical Environment with its own TDZ period. This is why the inner block shadowing trick works — the inner `let` is in TDZ in its block's LE, even before its declaration line.
</details>

---

**7.5** How does `var` vs `let`/`const` connect to Variable Environment vs Lexical Environment?

<details>
<summary>Answer</summary>

`var` lives in the Variable Environment — which is function-scoped. `let`/`const` live in the Lexical Environment — which is block-scoped. At global level, both point to the same object (so `var` at global scope IS accessible through the scope chain). Inside functions/blocks they separate, which is why `var` leaks out of blocks but `let`/`const` don't.
</details>

---

**7.6** How does pass-by-value-of-reference connect to memory leaks?

<details>
<summary>Answer</summary>

When you pass an object to a function (or store it in a variable, closure, or event listener), you're copying its reference — but that copied reference still keeps the object reachable from GC's perspective. If you never release that reference (set it to null, remove the listener, clear the timer), the object stays in memory even when you no longer need it. That's a memory leak.
</details>
