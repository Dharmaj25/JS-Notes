## Corrections to the earlier study notes (read once)

These were wrong or imprecise in the notes and are corrected throughout this bank:

1. **W2D2 Q9:** `foo(undefined, 2)` with `function foo(a = b, b = 2)` throws **ReferenceError**, not `4`. Parameters initialise left to right; `b` is still in TDZ when `a`'s default runs, *even though an argument for `b` was passed*. ✅
2. **Arrow functions and `arguments`:** an arrow has no *own* `arguments`, but inside a regular function it sees the **enclosing function's** `arguments`. It only throws `ReferenceError` when no enclosing function exists (see B27). ✅
3. **"Arrow `this` = global":** wrong as a rule. Arrow `this` is whatever the *enclosing scope's* `this` was. That is the global object only in a sloppy classic script's top level.
4. **"Promises solve inversion of control":** they *improve* it (a callback runs at most once, always asynchronously, errors are captured) but you still hand callbacks to someone else's `.then`.
5. **"`bind` uses `call` internally":** a teaching shortcut. Native `bind` creates a bound function exotic object. Our `myBind` is a *simplified* model.
6. **W2D6 Q5 and Q16** contained a garbled answer and a function mislabelled as `pipe`. Correct versions are B30 and A33/C20.

# SECTION A — Conceptual (35)

## A-1 · `this`

### A1 · this/Basics · What · Easy · Core
**Q:** What is `this`, and what decides its value?

**Answer:** `this` is a per-invocation binding stored in the function's execution context. For **regular functions** it is decided by the **call site** (how the function is called). For **arrow functions** there is no own binding; `this` is resolved lexically from the enclosing scope, fixed at creation.

**Explanation:** When a function is called, the engine creates an execution context and sets its `ThisBinding` from the call form (`new f()`, `f.call(x)`, `obj.f()`, `f()`). Arrow functions skip this step, so evaluating `this` inside them walks outward through lexical environments, exactly like a variable lookup.

**Misconception:** "`this` is the object the function was defined in."

**Follow-ups:**
1. Is `this` the same as scope? *(No. Scope is about variables; `this` is a separate binding.)*
2. What is top-level `this` in a browser script, Node CJS module, ES module? *(`window`, `module.exports`, `undefined`.)*
3. Does `this` follow the scope chain? *(Only for arrow functions.)*

### A2 · this/Binding rules · What · Easy · Core
**Q:** List the four binding rules in precedence order and how you identify each.

**Answer:**
1. **`new`**: `new F()` → `this` = freshly created object.
2. **Explicit**: `f.call(x)`, `f.apply(x)`, `f.bind(x)()` → `this` = `x`.
3. **Implicit**: `obj.f()` → `this` = `obj` (the base object immediately left of the dot).
4. **Default**: plain `f()` → `globalThis` (sloppy) or `undefined` (strict).

Arrow functions bypass all four.

**Explanation:** Check in order. Is it an arrow? Stop, use lexical `this`. `new`? Explicit? Dot call? Otherwise default.

**Misconception:** "`bind` is the strongest." `new` overrides a bound `this` (see A28/B25).

**Follow-ups:**
1. `obj.f.call(other)`: which wins? *(explicit)*
2. `bound.call(other)`: which wins? *(bind)*
3. `new bound()`: which wins? *(new)*

### A3 · this/Motivation · Why · Easy · Core
**Q:** Why does JavaScript have a dynamic `this` at all?

**Answer:** So **one function object can serve many receivers**: methods shared via a prototype, borrowed methods, constructor functions. Without it every method would hardcode a variable name (`user.name`) and break when reused.

**Explanation:** 1000 instances share one `Person.prototype.greet`. It must know *which* instance called it. Dynamic `this` provides that without creating 1000 closures.

**Misconception:** "`this` only matters for classes."

**Follow-ups:**
1. What is the cost of this flexibility? *(Lost-context bugs.)*
2. How could you avoid `this` entirely? *(Closures/factories, see F4.)*

### A4 · this/Arrow · How · Intermediate · Core
**Q:** How does an arrow function determine `this`? Is it the global object?

**Answer:** It has no `this` binding. When `this` is evaluated inside it, the engine looks outward through enclosing lexical environments until it finds a non-arrow function (or global/module code) that has a binding. So arrow `this` equals the enclosing `this` *at creation time*. It's the global object only when the enclosing context is sloppy classic-script top level.

**Explanation:**
```js
const o = { n: "o", get() { return () => this.n; } };
o.get()();            // "o"  (enclosing `get` had this=o)
const arrow = () => this; // top level: window / module.exports / undefined
```
**Misconception:** "Arrow `this` is always window."

**Follow-ups:**
1. Arrow as an object-literal property: what is `this`? *(Enclosing top-level `this`; object literals don't create a binding.)*
2. Can `call` change it? *(No; thisArg is ignored.)*
3. Arrow as a class field? *(Enclosing is the constructor, so `this` is the instance. Extension: classes.)*

### A5 · this/Lost context · Why · Easy · Core
**Q:** Why do detached methods lose `this`, and what are all the ways to fix it?

**Answer:** `const g = o.f` copies only the function reference. The call `g()` has no base object, so default binding applies. Fixes: `o.f.bind(o)`, wrapper `() => o.f()`, `f.call(o)`, and for classes: bind in the constructor or use an arrow class field. Or avoid `this` using closures.

**Explanation:** Binding is determined at *call*, and the call form `g()` is a plain call.

**Misconception:** "A function belongs to the object it was defined on."

**Follow-ups:**
1. Why does `setTimeout(o.f, 0)` lose it? *(The timer machinery calls it plain.)*
2. What does strict mode change? *(TypeError instead of silently reading from global.)*
3. Trade-offs of `bind` vs arrow wrapper? *(bind: new function, permanent; wrapper: extra frame, flexible args.)*

### A6 · this/Strict mode · Difference · Intermediate · Core
**Q:** How does strict mode change `this`?

**Answer:** Default binding gives `undefined` instead of `globalThis`. Also, `call/apply/bind` with a primitive or `null` thisArg: sloppy **boxes** primitives and substitutes `globalThis` for `null/undefined`; strict passes them through unchanged. ✅ (see B15)

**Explanation:** Strict mode removes the silent fallback that made detached-method bugs read from or write to the global object. Classes and ES modules are strict automatically.

**Misconception:** "Strict mode only affects undeclared variables."

**Follow-ups:**
1. `typeof this` inside `t.call(5)`: sloppy vs strict? *("object" vs "number")*
2. Why are detached class methods a TypeError? *(Class bodies are strict.)*

### A7 · this/new · How · Easy · Core
**Q:** What exactly does `new F(...)` do?

**Answer:** (1) Creates an object whose prototype is `F.prototype`; (2) calls `F` with `this` set to it; (3) if `F` returns an **object**, that object is the result; otherwise the new object is returned. Primitive return values are ignored. ✅ (B26)

**Explanation:** Arrow functions, method shorthands and bound arrows have no `[[Construct]]`, so `new` throws `TypeError`.

**Misconception:** "`new` always returns the `this` object."

**Follow-ups:**
1. What happens if you forget `new` on a constructor function? *(Default binding; sloppy mode pollutes global, strict throws.)*
2. `new.target`? *(Detects constructor invocation. Extension.)*

### A8 · this/Design · When · Intermediate · Core
**Q:** When should you use an arrow function and when a regular function?

**Answer:** **Arrow:** callbacks and inner helpers that must use the *outer* `this`; short pure transforms. **Regular/method shorthand:** object methods, prototype methods, constructors, anything needing dynamic `this`, own `arguments`, or `new`.

**Explanation:** Arrow as an object property captures the *outer* `this` and silently breaks `this.x` access.

**Misconception:** "Arrows are always better/modern."

**Follow-ups:**
1. Why not arrows on `Object.prototype`/prototype methods? *(Wrong `this`.)*
2. Class-field arrow trade-off? *(Stable `this`, but one function per instance.)*

## A-2 · Function fundamentals

### A9 · Functions/Declaration vs expression · Difference · Easy · Core
**Q:** Difference between a function declaration and a function expression?

**Answer:** A declaration (`function f(){}` as a statement) is hoisted **with its body** and creates a binding in the enclosing scope. An expression produces a function *value* (assignable, passable, returnable); only the *variable* hoists (as `undefined` for `var`, TDZ for `let/const`).

| | Declaration | Expression |
|---|---|---|
| Callable before line? | ✅ | ❌ |
| Name required? | yes | optional |
| Error if called early | none | `var`→TypeError, `let/const`→ReferenceError |

**Misconception:** "`const f = function(){}` is hoisted like a declaration."

**Follow-ups:**
1. Which error for `var f = function(){}` called early? *(TypeError: f is not a function)*
2. Declaration inside `if` blocks? *(Inconsistent legacy semantics; avoid.)*

### A10 · Functions/Hoisting · How · Intermediate · Core
**Q:** Walk through hoisting and TDZ for each way of creating a function.

**Answer:**
- Declaration: fully initialised in the creation phase.
- `var f = function` / `var f = () =>`: `f` is `undefined` until assignment.
- `let/const f = ...`: `f` exists but is in TDZ until its line runs.
- When a declaration and `var` share a name, the function wins during creation, and the `var` assignment then overwrites it at runtime. ✅ (B6)

**Misconception:** "`let` and `const` aren't hoisted." *(They are; TDZ proves it.)*

**Follow-ups:**
1. Does a `function` declaration inside another function hoist to the outer? *(No; only to its own scope.)*
2. Why does `typeof undeclared` not throw, but `typeof tdzVar` does?

### A11 · Functions/Named function expressions · What · Intermediate · Core
**Q:** What is a named function expression, and where is the name visible?

**Answer:** `const f = function g(){}`. `g` is bound **only inside the function body**, as an immutable binding. Outside, `g` is undeclared. Use cases: self-recursion that survives reassignment of `f`, readable stack traces, `fn.name`.

**Explanation:** Assigning to `g` inside is silently ignored in sloppy mode and a TypeError in strict mode ✅ (B22).

**Misconception:** "The name creates a variable in the enclosing scope" (that's declarations).

**Follow-ups:**
1. Recursion via `f` fails if…? *(`f` is reassigned.)*
2. Arrow functions: can they self-reference? *(Only through the variable that holds them.)*

### A12 · Functions/Arrow limitations · What · Easy · Core
**Q:** List the differences/limitations of arrow functions.

**Answer:** No own `this`, `arguments`, `super`, `new.target`; **not constructible** (no `[[Construct]]`, no `prototype`); can't be generators; `call/apply/bind` can't change `this` (arguments still pass; `bind` can still pre-fill args). Implicit return with expression bodies; wrap object literals in `()`.

**Explanation:** Arrows were designed for lexical `this` in callbacks, so everything about *own* identity was removed.

**Misconception:** "Arrows throw ReferenceError for `arguments`" (only when no enclosing function, see B27).

**Follow-ups:**
1. Use rest parameters instead of `arguments`; why? *(Real array, works in arrows.)*
2. `new` on a bound arrow? *(TypeError.)* ✅

### A13 · Functions/Default parameters · How · Intermediate · Core
**Q:** Explain default parameter semantics precisely.

**Answer:** A default applies only when the argument is **`undefined`** (missing or explicit `undefined`), not `null`, `0`, `""`, `false`, `NaN`. Defaults are **evaluated at each call**, left to right, in a parameter scope where earlier params are visible and *later ones are in TDZ*. ✅

**Explanation:**
```js
function f(a = b, b = 2) {}
f();            // ReferenceError
f(undefined,5); // ReferenceError (b not initialised when a's default runs)
f(1);           // OK (default for a not needed)
```
With defaults present, params get a **separate scope** from the body, so a default closure sees the outer `x`, not a body `let x`. ✅

**Misconception:** "Default objects are shared across calls." *(They're re-created per call.)*

**Follow-ups:**
1. `f(null)` for `f(x = 10)`? *(`null`.)*
2. Does a default expression with side effects run on every omitted call? *(Yes.)*
3. How do defaults affect `fn.length`? *(See A15.)*

### A14 · Functions/First-class · What · Easy · Core
**Q:** What does "functions are first-class" mean, and what does it enable?

**Answer:** Functions are ordinary values: assignable, passable, returnable, storable in data structures, and they carry properties. This enables HOFs, callbacks, closures, currying, composition.

**Misconception:** "First-class means functions are objects with methods only."

**Follow-ups:**
1. Give a language where this isn't true. *(Old C: function pointers only.)*
2. Why does first-class + lexical scope imply closures? *(Returned functions need their environment.)*

### A15 · Functions/Properties · What · Intermediate · Core
**Q:** What are `fn.name` and `fn.length`? What are the gotchas?

**Answer:** `name` is inferred from the binding/property (`const a = () => {}` → `"a"`; bound → `"bound f"`; double bound → `"bound bound f"` ✅). `length` is the number of parameters **before the first default or rest parameter** ✅: `(a,b)=>{}`→2, `(a,b=1)=>{}`→1, `(a,...r)=>{}`→1.

**Explanation:** `length` is what generic `curry` helpers read, so defaults/rest silently break them (A34, B29).

**Misconception:** "`length` counts all declared parameters."

**Follow-ups:**
1. `bind(null, 1, 2)` on a 3-param function: new `length`? *(1.)* ✅
2. Is `name` reliable for minified code? *(No.)*

## A-3 · Higher-order functions and callbacks

### A16 · HOF/Definition · What · Easy · Core
**Q:** What is a higher-order function? Give examples that return functions and that take functions.

**Answer:** A function that **takes** a function argument, **returns** a function, or both. Takes: `arr.map`, `setTimeout`, `addEventListener`. Returns: `makeMultiplier`, `bind`, decorators. Both: `compose`, `memoize`, `once`.

**Misconception:** "HOFs are only array methods."

**Follow-ups:**
1. Is `bind` a HOF? *(Yes: returns a function.)*
2. Is a function that only *calls* a global function a HOF? *(No.)*

### A17 · HOF/Callbacks · Difference · Intermediate · Core
**Q:** What is a callback? Is it always called later?

**Answer:** A function passed to another function to be invoked by it. **Not necessarily later**: `arr.map(cb)` and `sort(cb)` call it synchronously; `setTimeout(cb)` and event listeners call it asynchronously.

**Explanation:** Mixing sync and async paths in one API is a known hazard (sometimes-sync callbacks cause ordering bugs, see G12). Prefer consistently async or consistently sync.

**Misconception:** "Callback = asynchronous."

**Follow-ups:**
1. Output order for a sync vs async callback around `console.log`? *(Sync inline; async after current stack. Extension: event loop.)*
2. How should an API signal errors in callbacks? *(Node convention `cb(err, result)`.)*

### A18 · HOF/Inversion of control · Why · Intermediate · Extension
**Q:** What is inversion of control with callbacks, and do Promises solve it?

**Answer:** You hand your function to third-party code, trusting it to call it once, with the right arguments, at the right time, and not too early/late. Promises improve this: the handler runs **at most once**, **always asynchronously**, and errors are captured. They don't fully remove trust issues (you still pass handlers, thenables from untrusted sources need assimilation).

**Misconception:** "Callback hell = deep nesting only."

**Follow-ups:**
1. Name 3 broken guarantees of a callback. *(twice, never, sync-vs-async, wrong args, swallowed errors.)*
2. What does flattening the pyramid not fix? *(Trust.)*

### A19 · HOF/Distinction · Difference · Easy · Core
**Q:** What is the difference between a higher-order function and a callback?

**Answer:** They describe *roles*, not kinds of functions. The **HOF** is the function that receives/returns a function; the **callback** is the function being passed in. One function can be both (`compose` receives callbacks and returns a HOF).

**Follow-ups:** 1. Can a callback itself be a HOF? *(Yes.)* 2. Is `[1,2].map(x => x*2)`: which is which? *(`map` is the HOF; the arrow is the callback.)*

### A20 · HOF/Factories vs decorators · When · Intermediate · Core
**Q:** When do you write a function factory vs a decorator/wrapper?

**Answer:** **Factory:** create *configured* functions or private-state objects (`makeValidator(rules)`). **Decorator:** add cross-cutting behaviour (logging, timing, caching, retry, once) around an existing function without editing it, preserving `this`, arguments and return value.

**Explanation:** A decorator must forward `this` and all args and return the result, or it breaks the wrapped function (G1, B35).

**Misconception:** "Wrappers can use plain `fn(...args)`" (loses `this`).

**Follow-ups:** 1. What does a wrapper lose by default? *(`name`, `length`, properties.)* 2. Decorating a method vs a standalone function?

## A-4 · Closures

### A21 · Closures/Definition · What · Easy · Core
**Q:** Define a closure precisely.

**Answer:** A function bundled with a reference to the **lexical environment in which it was created**, so it can keep reading and writing those bindings even when called outside or after that scope has finished.

**Explanation:** Every function object records its creating environment (`[[Environment]]`). The closure is observable when it outlives the outer call.

**Misconception:** "A closure is a function inside a function that returns a function."

**Follow-ups:** 1. Is a callback inside `setTimeout` a closure? *(Yes, if it uses outer variables.)* 2. Do you need to return the function? *(No.)*

### A22 · Closures/Mechanics · How · Intermediate · Core
**Q:** How do closures work under the hood, and what about garbage collection?

**Answer:** Calling `outer()` creates a lexical environment holding its variables. Inner functions created there keep an outer-reference to it. After `outer` returns, its execution context is popped but that environment stays **reachable** via the inner function, so GC cannot reclaim it. When the inner function becomes unreachable, the environment can be collected, but **timing is not deterministic**.

**Explanation:** Engines optimise by retaining only *captured* variables, but in some engines (e.g. V8) variables captured by any closure from the same scope share one context object, so one long-lived closure can keep another's captured variables alive.

**Misconception:** "The entire outer function stays in memory."

**Follow-ups:** 1. Setting `fn = null`: will memory be freed immediately? *(No; it becomes eligible.)* 2. Spot a retention risk in a closure holding a big array.

### A23 · Closures/Capture semantics · How · Intermediate · Core
**Q:** Do closures capture values or variables? How is state shared or independent?

**Answer:** **Variables** (live bindings). Closures created in the *same* call share the same variables; closures from *separate* calls of the outer function have independent bindings. ✅ (B9, B10)

**Misconception:** "A closure freezes the value at creation."

**Follow-ups:** 1. What does `x = 2` after creating a closure over `x` do? *(Closure sees 2.)* 2. Two getters/setters from one factory call: shared or independent?

### A24 · Closures/Loops · Why · Intermediate · Core
**Q:** Explain the `var` loop closure bug and every way to fix it.

**Answer:** `var i` is one function-scoped binding shared by all callbacks; they run after the loop and see the final value. Fixes: `let` (new binding per iteration), IIFE passing `i`, a helper function/`forEach`-style callback parameter, `bind`/extra argument to `setTimeout`.

**Explanation:** With `let`, the engine **copies** the loop variable into a fresh binding each iteration *before* the increment. Mutating `i` inside the body affects that iteration's binding only: `for(let i=0;i<3;i++){fns.push(()=>i);i++}` → `[1,3]` ✅ (B31).

**Misconception:** "`let` makes closures capture by value."

**Follow-ups:** 1. Why doesn't `const` work in a classic `for`? *(`i++` assigns.)* 2. Output of the `[1,3]` snippet.

### A25 · Closures/Memory · When · Advanced · Core
**Q:** When do closures cause memory problems and how do you prevent them?

**Answer:** Typical retention: unbounded memoize caches, event listeners/timers never removed, closures capturing big objects they barely use, long-lived registries of callbacks. Prevent: remove listeners/clear timers, null references, bound caches (LRU), `WeakMap` for object-keyed caches, capture only what's needed (copy small values out of big structures).

**Misconception:** "Closures always leak." *(They retain reachability only while the closure is reachable.)*

**Follow-ups:** 1. Why can `WeakMap` help a memoize? *(Keys don't keep objects alive.)* 2. How would you detect it? *(Heap snapshot diff.)*

### A26 · Closures/Terminology · Difference · Intermediate · Core
**Q:** Difference between scope, lexical environment, and closure? Is every function a closure?

**Answer:** **Scope** is the *rules/region* where a name resolves. A **lexical environment** is the *runtime structure* (record + outer reference) implementing it. A **closure** is a *function plus its environment*. Technically every function has `[[Environment]]`; in practice we say "closure" when that environment matters, i.e. it is used after the creator returned.

**Misconception:** "Closure and scope are synonyms."

**Follow-ups:** 1. Is a top-level function a closure over global? *(Technically yes; practically uninteresting.)* 2. Does a closure copy the scope chain? *(No, references it.)*

## A-5 · call / apply / bind

### A27 · Binding/Comparison · Difference · Easy · Core
**Q:** Difference between `call`, `apply` and `bind`?

**Answer:** `call(thisArg, a, b)` invokes now with individual args. `apply(thisArg, [a, b])` invokes now with an **array-like** (arrays *and* `{length:n,0:…}`) ✅ (B24). `bind(thisArg, ...pre)` **returns a new function**, doesn't invoke, with `this` permanently set and optional pre-filled args.

**Follow-ups:** 1. Which return the function's result? *(call, apply; bind returns the bound function.)* 2. `apply` today vs spread? *(Spread replaced most uses.)*

### A28 · Binding/Precedence · How · Advanced · Core
**Q:** Can a bound function's `this` be overridden? What about `new`?

**Answer:** `call`, `apply` and a second `bind` cannot override it. **`new` does**: constructing a bound function ignores the bound `this`, constructs the *target* with the new object, prepends the pre-filled args. `p instanceof Target` and `p instanceof Bound` are both true. ✅ (B25)

**Misconception:** "`bind` is unbreakable."

**Follow-ups:** 1. Does a bound function have `prototype`? *(No.)* 2. What is `bound2.name` after double bind? *("bound bound f")* ✅

### A29 · Binding/Usage · When · Intermediate · Core
**Q:** When do you choose each of the three?

**Answer:** `call`: invoke now with known args, borrow a method. `apply`: args already in an array/array-like (legacy; prefer spread). `bind`: hand a function to someone else (callback, listener) with fixed `this`/leading args; partial application.

**Follow-ups:** 1. Why is `removeEventListener(type, fn.bind(x))` wrong? *(New function each time, E4.)* 2. `bind` vs arrow wrapper?

### A30 · Binding/thisArg edge cases · How · Advanced · Core
**Q:** What happens when `thisArg` is `null`, `undefined`, or a primitive?

**Answer:** Sloppy: `null`/`undefined` → `globalThis`; primitives are **boxed** (`typeof this` → `"object"`). Strict: used as-is (`"number"`, `null`). ✅ (B15) Passing `null` is fine only when the function doesn't use `this` (`Math.max.apply(null, arr)`).

**Misconception:** "`call(null)` makes `this` null."

**Follow-ups:** 1. Which is safer, `null` or `undefined`? *(Equivalent; be consistent.)* 2. What does a custom `myCall` need to mirror? *(C10.)*

### A31 · Binding/Special functions · How · Advanced · Core
**Q:** What happens when you use `call/apply/bind` on arrow functions and classes?

**Answer:** Arrow: `thisArg` ignored; arguments still forwarded; `bind(null, x)` still pre-fills (partial application); `new` on it throws. Class: calling with `.call()` throws `TypeError` (classes require `new`) ✅; `bind` works and `new` on the bound class works.

**Follow-ups:** 1. Why does an arrow ignore thisArg? *(No own binding to set.)* 2. Is `bind` on an arrow useful at all? *(Only for args.)*

## A-6 · Advanced functions

### A32 · Advanced/Currying · Difference · Intermediate · Core
**Q:** Currying vs partial application?

**Answer:** **Currying** converts `f(a,b,c)` into `f(a)(b)(c)`: a chain of unary functions. **Partial application** fixes *some* arguments now and returns a function taking the rest in one or more steps (`f.bind(null,a)` → `g(b,c)`). Currying is a transformation of the function; partial application is a use of it.

**Follow-ups:** 1. Is `bind` currying? *(No, partial.)* 2. Is `add(1)(2,3)` valid with a strict curry? *(No; flexible curries allow it.)*

### A33 · Advanced/Composition · How · Intermediate · Core
**Q:** What are `compose` and `pipe`? How do they differ and what should functions look like?

**Answer:** Both chain functions so one's output feeds the next. `compose(f,g,h)(x) = f(g(h(x)))` (right to left); `pipe(h,g,f)(x)` (left to right). Stages should be **unary** (one input) except possibly the first. Curried helpers fit well.

**Misconception:** "`compose` and `pipe` give different results." *(Same result if order is reversed.)* **Predicate composition** (`and/or/not`) is *not* pipe: each predicate sees the *same* input, not the previous output.

**Follow-ups:** 1. Implement with `reduce`/`reduceRight`. 2. How would you support async stages? *(Extension.)*

### A34 · Advanced/Arity · Why · Advanced · Core
**Q:** Why is `Function.length` unreliable for a generic `curry`?

**Answer:** It excludes parameters from the first default onward and rest parameters, and is `0` for variadics. `curry((a,b=2,c)=>…)` thinks arity is 1 and fires after one argument ✅ (B29). Fix: `curryN(fn, arity)` with explicit arity.

**Follow-ups:** 1. What does `curry` do with extra args? *(Passes them; 4 args to a 3-arity function.)* 2. Placeholder support?

### A35 · Advanced/Trade-offs · When · Advanced · Core
**Q:** When is currying valuable, and when is it overkill?

**Answer:** Good: config-first/data-last APIs, reusable specialised functions, point-free pipelines. Bad: variadic or optional-arg functions, hot paths (extra closures), team unfamiliarity, hard debugging/stack traces. Often plain partial application or a small wrapper is clearer.

**Follow-ups:** 1. Example where currying hurts readability? 2. `map(parseInt)`: how does arity bite? *(G13.)*

### C4 · Closures/Memoize (single arg) · Intermediate · Core
**Problem:** `memoize(fn)` caching results by the single argument.
```js
function memoize(fn) {
  const cache = new Map();
  return function (arg) {
    if (cache.has(arg)) return cache.get(arg);
```

```js
    if (cache.has(key)) return cache.get(key);
    const r = fn.apply(this, args);
    cache.set(key, r);
    return r;
  };
}
```
**Explanation:** The resolver turns an argument list into a stable key.
**Edge cases:** `JSON.stringify` drops `undefined`/functions, throws on circular structures, treats `{a:1,b:2}` ≠ `{b:2,a:1}`; argument order matters (`add(1,2)` vs `add(2,1)` cached separately).
**Common mistakes:** `args.join(",")` (`[1,"2"]` vs `["1,2"]` collisions); caching rejected/thrown results.
**Follow-ups:** (1) Provide a resolver for one-object-arg functions. (2) Should errors be cached? (3) How does a stale cache arise with impure `fn`?

### C6 · Closures/Once · Intermediate · Core
**Problem:** `once(fn)`: runs `fn` the first time, then returns the first result forever.
```js
function once(fn) {
  let called = false, result;
  return function (...args) {
    if (!called) { called = true; result = fn.apply(this, args); }
    return result;
  };
}
```
**Explanation:** Flag + cached result in closure; `apply(this, args)` preserves context.
**Edge cases:** If `fn` **throws**, the flag is already set → later calls return `undefined`. Variant that allows retry after failure:
```js
function onceSafe(fn) {
  let called = false, result;
  return function (...args) {
    if (called) return result;
    result = fn.apply(this, args);
    called = true;            // set only after success
    return result;
  };
}
```
**Common mistakes:** returning `undefined` on later calls; not forwarding `this`.
**Follow-ups:** (1) Re-entrancy: what if `fn` calls the wrapper? (2) Make it async-aware. *(Extension.)*

### C7 · HOF/Transformation utility · Easy · Core

**Explanation:** HOF taking a callback; `call` supplies `thisArg` as `map` does.

## C-3 · call / apply / bind (simplified models)

### C10 · Binding/myCall · Advanced · Core
**Problem:** Implement `Function.prototype.myCall(thisArg, ...args)`.
```js
Function.prototype.myCall = function (thisArg, ...args) {
  if (typeof this !== "function") throw new TypeError("not callable");
  const ctx = thisArg == null ? globalThis : Object(thisArg);   // sloppy semantics
  const key = Symbol("fn");
  ctx[key] = this;
  try { return ctx[key](...args); }
  finally { delete ctx[key]; }
};
```
**Explanation:** Attach the function temporarily as a method of the target (implicit binding does the work) under a unique `Symbol` key to avoid clobbering properties; always clean up.
**Honest limitations:** mirrors **sloppy-mode** coercion only (strict native `call` doesn't box primitives or replace `null`); **fails on frozen/non-extensible targets** ✅ (native works); shows up in `Object.getOwnPropertySymbols` momentarily; not spec-exact.
**Common mistakes:** using a string key like `"fn"`; not deleting; returning nothing.
**Follow-ups:** (1) Why Symbol? (2) Alternative with `Reflect.apply(this, thisArg, args)`, what makes that exact? (3) What breaks for frozen objects?

### C11 · Binding/myApply · Advanced · Core
**Problem:** `myApply(thisArg, argsArray)`.
```js
Function.prototype.myApply = function (thisArg, argsArray) {
  if (typeof this !== "function") throw new TypeError("not callable");
  const ctx  = thisArg == null ? globalThis : Object(thisArg);
  const args = argsArray == null ? [] : Array.from(argsArray);   // array-like support
  const key  = Symbol("fn");
  ctx[key] = this;
  try { return ctx[key](...args); }
  finally { delete ctx[key]; }
};
```
**Explanation:** `Array.from` accepts array-likes (`{length:2,0:5,1:5}`) ✅.
**Honest limitations:** same as C10; native throws `TypeError` for non-object `argsArray` (e.g. a number); this model is lenient.
**Follow-ups:** (1) Why can `apply` accept `arguments` objects? (2) Implement `myCall` via `myApply`.

### C12 · Binding/myBind (basic) · Intermediate · Core
**Problem:** `myBind(thisArg, ...preset)` returning a function.
```js
Function.prototype.myBind = function (thisArg, ...preset) {
  const fn = this;
  if (typeof fn !== "function") throw new TypeError("not callable");
  return function (...later) { return fn.apply(thisArg, [...preset, ...later]); };
};
```
**Explanation:** The returned function is a closure over `fn`, `thisArg`, `preset`.
**Honest limitations:** ignores `new`; wrong `name` (`""` vs `"bound f"`) and `length`; returned function *has* a `prototype`; the `thisArg` primitive isn't coerced the way native does for sloppy targets.
**Common mistakes:** dropping the return value; losing pre-set args; calling immediately.
**Follow-ups:** (1) Verify `bound.call(other)` ignores `other` ✅. (2) Add `new` support (C13).

### C13 · Binding/myBind (with new) · Advanced · Core
**Problem:** Make the bound function behave correctly under `new`.
```js
Function.prototype.myBind2 = function (thisArg, ...preset) {
  const target = this;
  if (typeof target !== "function") throw new TypeError("not callable");
  function bound(...later) {
    const args = [...preset, ...later];
    if (new.target)                                       // called with new
      return Reflect.construct(target, args, new.target === bound ? target : new.target);
    return target.apply(thisArg, args);
  }
  bound.prototype = target.prototype;                     // so instanceof works
  return bound;
};
```
**Explanation:** Under `new`, the bound `thisArg` must be **ignored** (B25); construct the *target* instead. `Reflect.construct` also works for ES `class` targets ✅ (tested with a class). Setting `bound.prototype` makes `p instanceof Bound` true; native bound functions achieve this differently (they have no `prototype` and delegate `instanceof` to the target).
**Honest limitations:** still no correct `name`/`length`; `bound.prototype === target.prototype` is a shortcut.
**Follow-ups:** (1) Why not `this instanceof bound`? *(Fails for subclasses/`Reflect.construct` cases; `new.target` is robust.)* (2) Set `name`/`length` with `Object.defineProperty`.

### C14 · Binding/Method borrowing · Intermediate · Core
**Problem:** Implement `borrowMethod(source, name, target)` and convert an `arguments`-style object to an array.

**Explanation:** `Array.prototype.slice` works on any array-like because it only reads `length` and indices.

## C-4 · Currying, partial application, composition

### C15 · Currying/Generic curry · Advanced · Core
**Problem:** `curry(fn)` that accepts arguments in any grouping.
```js
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) return fn.apply(this, args);
    return function (...more) { return curried.apply(this, [...args, ...more]); };
  };
}
const add = curry((a, b, c) => a + b + c);
add(1)(2)(3); add(1, 2)(3); add(1)(2, 3); add(1, 2, 3); // all 6
```
**Explanation:** Collect arguments across calls; invoke once `args.length >= fn.length`.
**Edge cases:** defaults/rest break `fn.length` (B29); zero-arity functions invoke immediately; extra args are forwarded (`add(1,2,3,4)` → 6); `undefined` passed explicitly still counts as an argument.
**Complexity:** O(k) per call chain with array copying; closures retained until invoked.
**Common mistakes:** checking `args.length === fn.length` (breaks over-application); losing `this`; forgetting to pass accumulated args.
**Follow-ups:** (1) Add placeholder support. (2) Make `curry` handle methods (`this`). (3) Memory cost?

### C16 · Currying/curryN · Advanced · Core
**Problem:** Handle functions with defaults/rest by specifying arity explicitly.
```js
function curryN(fn, arity) {
  return function curried(...args) {
    if (args.length >= arity) return fn.apply(this, args);
    return (...more) => curried.apply(this, [...args, ...more]);
  };
}
const k = curryN((a, b = 2, c) => [a, b, c], 3);
k(1)(2)(3); // [1, 2, 3]
```
**Explanation:** The caller declares the real arity; `fn.length` is bypassed.
**Edge cases:** arity ≤ 0; `arity` greater than what callers pass → never invokes.
**Follow-ups:** (1) Default `arity = fn.length`. (2) When is explicit arity better than inference?

### C17 · Partial/partial & partialRight · Intermediate · Core

### C18 · Composition/compose · Intermediate · Core
**Problem:** `compose(...fns)(x) = f1(f2(...fn(x)))`.
```js
const compose = (...fns) => {
  fns.forEach(f => { if (typeof f !== "function") throw new TypeError("functions only"); });
  return x => { let acc = x; for (let i = fns.length - 1; i >= 0; i--) acc = fns[i](acc); return acc; };

```
**Explanation:** Iterate right to left feeding each result forward. Validate up front: a bad stage should fail at construction, not at call time.
**Edge cases:** no functions → identity; multi-argument first function; stage returning `undefined`.
**Common mistakes:** **`fns.reverse()` mutates the caller's array** (D16); applying left to right.

### C20 · Composition/Predicate combinators · Intermediate · Core
**Problem:** `and`, `or`, `not` for predicates.
```js
const and = (...ps) => function (...args) { return ps.every(p => p.apply(this, args)); };
const or  = (...ps) => function (...args) { return ps.some (p => p.apply(this, args)); };
const not = p => function (...args) { return !p.apply(this, args); };

```
**Explanation:** Every predicate receives the **same** input and results are combined with boolean logic; this is **not** `pipe` (where each stage gets the previous *output*).

### C21 · Composition/Validator builder · Intermediate · Core

### C22 · Closures/before & after · Intermediate · Core
**Problem:** `after(n, fn)` runs `fn` from the n-th call on; `before(n, fn)` runs it for the first n calls then reuses the last result.

### C23 · Closures/State container · Advanced · Core

### C25 · HOF/Retry wrapper · Intermediate · Core

# SECTION D — Debugging and code review (20)

### D1 · this/Detached method in a timer · Easy · Core
```js
const timer = {
  seconds: 0,
  tick() { this.seconds++; console.log(this.seconds); },
  start() { setInterval(this.tick, 1000); }
};
timer.start();
```
**Problem:** Prints `NaN` forever (or throws in strict mode); `timer.seconds` stays `0`.
**Diagnosis:** `this.tick` passes a *detached* function; the timer calls it without a receiver → default binding → writes `globalThis.seconds`.
**Fix:**
```js
start() { setInterval(() => this.tick(), 1000); }     // arrow wrapper
// or: setInterval(this.tick.bind(this), 1000);
```
**Hidden issue:** The interval id is discarded, so it can never be cleared; calling `start()` twice doubles the ticking.
**Follow-ups:** (1) Store and clear the id. (2) Prefer `bind` or arrow wrapper? *(Arrow wrapper reads the current `this.tick` at call time; `bind` freezes the function now.)*

```js
let calls = 0;
const f = memo(x => { calls++; return x * 0; });
f(5); f(5); console.log(calls);   // 2, expected 1
```
**Diagnosis:** Falsy results (`0`, `""`, `false`, `null`) look like cache misses ✅.
**Fix:** `Map` with `has`, or `x in c` / `c[x] !== undefined` check (C4).
**Hidden issue:** Keys are coerced to strings (B33).
**Follow-ups:** (1) Why not `c.hasOwnProperty(x)`? *(`"__proto__"`, `"constructor"` keys.)* (2) Use `Object.create(null)` or `Map`.

### D12 · Closures/Memoize with object args · Advanced · Core
```js
const memo = fn => { const c = {}; return o => c[o] || (c[o] = fn(o)); };
const f = memo(o => o.id);
f({ id: 1 }); console.log(f({ id: 2 }));   // 1 ✗
```
**Diagnosis:** Objects coerce to `"[object Object]"`: all objects share one key ✅.
**Fix:** `Map` keyed by identity, or a resolver such as `o => o.id` / `JSON.stringify`.
**Hidden issue:** Identity keys mean `{id:1}` created twice are different keys (cache never hits) and prevent GC unless a `WeakMap` is used.
**Follow-ups:** (1) Identity vs structural key trade-off. (2) `WeakMap` for object keys.

### D13 · Binding/Broken bind · Intermediate · Core
```js
Function.prototype.badBind = function (ctx) {
  const fn = this;
  return function () { fn.call(ctx); };
};
function g(a) { return this.n + a; }
console.log(g.badBind({ n: 1 })(2));   // NaN? undefined?
```
**Problem:** Returns `undefined`; arguments dropped too.
**Diagnosis:** Missing `return`, and arguments not forwarded ✅.
**Fix:** `return function (...later) { return fn.apply(ctx, [...pre, ...later]); }` (C12).
**Hidden issues:** No partial-arg support; no `new` handling (C13).
**Follow-ups:** (1) Which two properties must a bound wrapper preserve? (2) What does native do with `name`?

### D14 · Currying/Default param arity · Advanced · Core
```js
const curry = fn => function c(...a) { return a.length >= fn.length ? fn(...a) : (...b) => c(...a, ...b); };
const f = (a, b = 2, c = 3) => a + b + c;
console.log(curry(f)(1));        // 6, but…
console.log(curry(f)(1)(10));
```
**Problem:** The second call throws `TypeError` (`6` is not a function).
**Diagnosis:** `f.length === 1`, so the curry fires after one argument ✅.
**Fix:** `curryN(f, 3)` (C16) or document that defaults/rest aren't supported.
**Follow-ups:** (1) How do other libraries handle this? *(Explicit arity.)* (2) Rest-parameter functions: what arity?

### D15 · Composition/Wrong order · Easy · Core
```js
const compose = (...fns) => x => fns.reduce((acc, fn) => fn(acc), x);
console.log(compose(x => x + 1, x => x * 2)(5));   // expected 11
```
**Problem:** `12`.
**Diagnosis:** `reduce` runs left→right; that's `pipe` ✅.
**Fix:** `reduceRight`.
**Hidden issue:** The name lies; either rename it or fix semantics. Tests with only commutative stages (e.g. `+1`, `+2`) will not catch it.
**Follow-ups:** (1) Write a test that distinguishes them. (2) Implement `compose` via `pipe`.

### D16 · Composition/Mutating reverse · Advanced · Core
```js
const pipe = fns => x => fns.reduce((a, f) => f(a), x);
const compose = fns => pipe(fns.reverse());       // reverse() mutates!
const arr = [x => x + 1, x => x * 2];
const c1 = compose(arr); const c2 = compose(arr);
console.log(c1(5), c2(5));
```
**Problem:** Prints `12 12`; expected `11 11` ✅. `c1(5)` is correct (`11`) if called *right after* creation, but creating `c2` reverses the **same array** back, so `c1` silently changes behaviour and `c2` is wrong from the start.
**Diagnosis:** `Array.prototype.reverse` mutates the caller's array.
**Fix:** `pipe([...fns].reverse())` or `fns.slice().reverse()`.
**Hidden issue:** Captured arrays in closures should be copied defensively.
**Follow-ups:** (1) Which array methods mutate? (2) Why is a *captured* mutable array a hazard?

### D17 · Functions/Missing return · Easy · Core
```js
const double = x => { x * 2 };
console.log(double(2));
```
**Problem:** `undefined`.
**Diagnosis:** Braces create a block body; no `return`.
**Fix:** `x => x * 2` or `x => { return x * 2; }`.
**Hidden issue:** Returning an object literal needs parentheses: `x => ({ v: x })`.
**Follow-ups:** (1) Why does `{ v: x }` parse as a block with a label? (2) Linter rule?

### D18 · Functions/ASI return · Intermediate · Core
```js
function getUser() {
  return
  { name: "Asha" };
}
console.log(getUser());
```
**Problem:** `undefined`.
**Diagnosis:** Automatic semicolon insertion after `return` ✅.
**Fix:** put `{` on the same line.
**Follow-ups:** (1) Other ASI hazards: lines starting with `(` or `[`. (2) Why do many teams use Prettier/semicolons?

### D19 · HOF/Callback invoked twice · Advanced · Core
```js
function fetchData(cb) {
  try { const data = load(); cb(null, data); }
  catch (e) { cb(e); }
}
```
**Problem:** If `cb(null, data)` itself throws, the `catch` calls `cb(e)` *again*: the callback runs twice ✅.
**Diagnosis:** The callback call sits inside the `try` meant for `load()`.
**Fix:**
```js
function fetchData(cb) {
  let data, err = null;
  try { data = load(); } catch (e) { err = e; }
  cb(err, data);
}
```
**Hidden issue:** Mixing sync and async invocation (G12) and not guaranteeing "once".
**Follow-ups:** (1) Wrap `cb` with `once`. (2) How do promises avoid this?

### D20 · Code review/Needless complexity · Intermediate · Core
```js
var makeAdder = function (x) {
  return (function () {
    var y = x;
    return function (z) { return y + z; };
  })();
};
```
**Works, but:** The IIFE and copy of `x` add nothing (parameters are already per-call bindings); `var` obscures scope; a function expression is used where an arrow/declaration is clearer.
**Rewrite:** `const makeAdder = x => z => x + z;`
**Review checklist you should voice:** unnecessary closure layers; `var`; no validation if inputs must be numbers; naming; does it need to be curried at all?
**Follow-ups:** (1) When *is* an IIFE justified? *(Pre-ES6 private scope; one-off init.)* (2) Would you ever write this with `bind`?

# SECTION E — Practical frontend scenarios (15)

React is the *context*; the questions test JavaScript. Each answer separates **JS behaviour** from **React-specific behaviour**.

### E1 · this/Class component handler · Easy · Core
```jsx
class Save extends React.Component {
  handle() { this.setState({ saved: true }); }
  render() { return <button onClick={this.handle}>Save</button>; }
}
```
**Problem:** Clicking throws `Cannot read properties of undefined (reading 'setState')`.
**JS vs React:** *JS:* `this.handle` is extracted; class bodies are strict, so default binding gives `undefined`. *React:* it invokes handlers without a receiver.
**Fix:** `constructor(){ this.handle = this.handle.bind(this); }`, or an arrow class field `handle = () => {…}`, or `onClick={() => this.handle()}`.
**Follow-ups:** (1) Trade-offs of each fix (per-instance function vs per-render function). (2) Why isn't this a problem in function components? *(No `this`; closures.)*

### E2 · Closures/Inline arrow identity · Intermediate · Core
```jsx
<Child onSelect={() => select(id)} />    // new function every render
```
**Question:** Is this a bug?
**Answer:** *JS:* every evaluation of an arrow expression creates a **new function object** (`(()=>{}) !== (()=>{})`). *React:* it only matters if `Child` is memoised (`React.memo`) or the function is a hook dependency, because identity changes force re-renders/effect re-runs. Otherwise it's fine; don't pre-optimise.
**Fix when needed:** `useCallback` (React-specific), or pass data and let the child call `onSelect(id)`.
**Follow-ups:** (1) Why doesn't `useCallback` stop the function *creation*? (2) When is `bind` in render worse? *(Always new function.)*

### E3 · Closures/Stale closure · Advanced · Core
```jsx
function Counter() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => setCount(count + 1), 1000);
    return () => clearInterval(id);
  }, []);
  return <p>{count}</p>;
}
```
**Problem:** The counter goes to `1` and sticks.
**JS vs React:** *JS:* closures capture bindings. *React:* **each render is a new call** of `Counter` with its own `count` binding; the effect from render 1 closed over `count = 0` and never re-runs (empty deps).
**Fix:** `setCount(c => c + 1)` (no captured value), or include `count` in deps (re-creating the interval).
**Follow-ups:** (1) Why does the updater form fix it? (2) How does a `useRef` solve similar problems?

### E4 · Binding/Removing listeners · Intermediate · Core
```js
el.addEventListener("click", this.onClick.bind(this));
// later
el.removeEventListener("click", this.onClick.bind(this));   // doesn't remove
```
**Problem:** Listener leaks.
**Diagnosis (pure JS/DOM):** each `bind` creates a *new function*, but removal needs the **same reference**.
**Fix:** `this.onClickBound = this.onClick.bind(this)` once; add and remove that.
**Follow-ups:** (1) Same issue with inline arrows. (2) `AbortController` signal as an alternative. *(Extension.)*

### E5 · Closures/Timer cleanup · Intermediate · Core
```js
function startPolling(update) {
  const id = setInterval(update, 1000);
  return () => clearInterval(id);       // closure holds id
}
const stop = startPolling(refresh);
```
**Question:** Why return a function? What leaks if you don't?
**Answer:** The closure keeps the private `id` so only the owner can stop it; otherwise the interval and everything `update` captures stay reachable forever.
**Follow-ups:** (1) How does `useEffect` cleanup mirror this? (2) What if `stop` is called twice? *(Harmless.)*

### E6 · Closures/Per-item handlers · Intermediate · Core
```jsx
{items.map(item => <li key={item.id} onClick={() => select(item.id)}>{item.name}</li>)}
```
**Question:** Why does each handler select the right item? Rewrite with a `var` loop and show the bug.
**Answer:** The arrow is created inside the callback, so each captures *its own* `item`. With `for (var i…) { li.onclick = () => select(items[i].id) }` all handlers see the final `i`.
**Follow-ups:** (1) Single handler + `data-id` (event delegation) vs closure per item. (2) Memory implications for 10 000 items.

### E7 · Composition/Form validation · Intermediate · Core
**Problem:** Compose reusable validators: required, min length, matches pattern.
```js
const required  = v => v != null && v !== "";
const minLen    = n => v => String(v).length >= n;
const matches   = re => v => re.test(v);
const validPass = and(required, minLen(8), matches(/\d/));   // `and` from C20
```
**Answer:** Predicate composition (all see the same value), built from curried factories. For *messages*, use `createValidator` (C21) so all failures are reported.
**JS vs React:** purely JS; React only calls it from `onChange`/`onSubmit`.
**Follow-ups:** (1) Async validation (unique username). (2) Cross-field validation: why predicates of one value aren't enough.

### E8 · HOF/Handler decorator · Intermediate · Core
```js
const withTracking = (name, handler) => function (...args) {
  analytics.track(name);
  return handler.apply(this, args);
};
<button onClick={withTracking("save_click", onSave)} />
```
**Answer:** A decorator that forwards `this`, arguments (the event) and return value. React specifics: synthetic event object (pooled in old versions), and the wrapper identity changes if created in render.
**Follow-ups:** (1) Where to create the wrapper to keep identity stable? (2) Should tracking errors break the handler? *(try/catch around tracking.)*

### E9 · Closures/Memoization vs useMemo · Advanced · Core
**Problem:** `formatCurrency(amount, locale)` is expensive and called for many rows. Memoize it.
**Answer:** *JS:* a closure-based cache keyed by `(amount, locale)` (C5) shared by all callers across renders. *React:* `useMemo` caches **per component instance, per dependency list**, and React may discard it. Different tools: pure-function cache vs render-scoped cache.
**Trade-offs:** unbounded growth (LRU); `JSON.stringify` key cost; impure functions invalidate the idea.
**Follow-ups:** (1) When is a manual cache wrong? *(time-dependent output)* (2) Memory impact of caching per row.

### E10 · Closures/Module pattern for config · Intermediate · Core
```js
const Config = (function () {
  let env = "dev";
  return { setEnv(e) { env = e; }, getEnv: () => env };
})();
```
**Answer:** The IIFE gives private state and a public API: the **module pattern**. Today an ES module gives file-level privacy by default and a singleton instance per module.
**Follow-ups:** (1) Testing hazards of module singletons. (2) How is this different from a class?

### E11 · Binding/Method as callback prop · Intermediate · Core
```jsx
<Form onSubmit={api.save} />      // api.save uses this.baseUrl
```
**Problem:** `this` is undefined/global inside `save`.
**Answer:** The method is detached when passed as a prop. Fix with a wrapper `values => api.save(values)`, `api.save.bind(api)`, or build `api` with closures (no `this`).
**JS vs React:** purely JS binding; React simply calls the prop.
**Follow-ups:** (1) Which fix survives later replacement of `api.save`? (2) Why do closure-based services avoid this class of bug?

### E12 · Composition/Request wrappers · Advanced · Core
```js
const request = url => doFetch(url);                  // placeholder
const client = compose(withLogging, withRetry(3), withAuth)(request);
```
**Question:** Does order matter? Which wraps which?
**Answer:** Yes. With `compose(a, b, c)(request)` the *rightmost* wraps first: `a(b(c(request)))`: `withLogging` is outermost, so it observes retries and auth as one call; reversing changes what is logged and whether auth headers are re-applied per retry.
**Follow-ups:** (1) Write the order as a pipe. (2) Which middleware should be outermost for error reporting?

### E13 · Composition/Data normalisation · Intermediate · Core
**Problem:** Turn an API payload into a UI model.
```js
const toUi = pipe(
  parse,                 // string → object
  pickFields,            // keep needed fields
  withDefaults,          // fill missing values
  formatDates            // locale formatting
);
```
**Answer:** Small unary pure stages are individually testable. Mutating a shared object between stages breaks purity (D16-style hazards). Decide how errors propagate (throw early vs result objects).
**Follow-ups:** (1) Insert a debug `tap` stage. (2) Convert the pipeline to async.

### E14 · Closures/Once-only submit · Intermediate · Core
```js
const submitOnce = once(() => api.submit(form));
button.addEventListener("click", submitOnce);
```
**Answer:** `once` (C6) prevents double submissions even with fast double-clicks. Caveats: if submit **fails**, `once` will never retry (use `onceSafe`, or reset state); the cached result is shared; disable the button as UX too.
**Follow-ups:** (1) How does React 18 StrictMode double-effect affect once-style initialisation? (2) Compare with debouncing. *(Extension.)*

### E15 · Currying/Handlers by field · Intermediate · Core
```jsx
const handleChange = field => e => setForm(f => ({ ...f, [field]: e.target.value }));
<input onChange={handleChange("email")} />
```
**Answer:** A curried handler factory creating one closure per field. Alternative: one handler reading `e.target.name`. Currying is concise but creates new functions each render.
**JS vs React:** closure/currying is JS; re-render consequences are React.
**Follow-ups:** (1) Which is friendlier to memoised inputs? (2) Typed version in TypeScript.

# SECTION F — Design patterns and abstractions (10)

These are ordinary function techniques; the names are conventional labels, not formal GoF patterns.

### F1 · Closures/Module pattern (IIFE) · Intermediate · Core
**Problem solved:** Private state and a public API without classes, before ES modules.
```js
const Counter = (function () {
  let count = 0;                          // private
  return { inc: () => ++count, get: () => count };
})();
```
**When:** one-off singleton with hidden state. **Trade-offs:** hard to test/reset; single instance; ES modules now give file-level privacy.
**Practical example:** feature-flag store, config holder (E10).
**Follow-ups:** (1) How do you reset it in tests? (2) Module pattern vs ES module singleton.

### F2 · Closures/Revealing module · Intermediate · Core
**Problem solved:** Define everything privately, then *reveal* only selected members, so internal calls don't depend on the public object (and `this`).
```js
const Cart = (function () {
  const items = [];
  function add(i)   { items.push(i); }
  function total()  { return items.reduce((s, i) => s + i.price, 0); }
  function size()   { return items.length; }
  return { add, total, size };           // reveal
})();
```
**When:** readability and consistent internal references. **Trade-offs:** replacing a public method later doesn't affect internal callers (a feature and a gotcha); exposed references to mutable internals (G7).
**Follow-ups:** (1) Why is `this` unnecessary here? (2) Mocking a public method for tests.

### F3 · Functions/Factory vs constructor · Intermediate · Core
**Problem solved:** Create objects without `new`/`this` pitfalls.
```js
function createUser(name) {
  let loginCount = 0;
  return { name, login() { loginCount++; return loginCount; } };
}
```
**When:** private state, no inheritance needed, call-without-`new` safety. **Trade-offs:** methods are recreated per instance (memory), no prototype sharing, `instanceof` doesn't work; constructors/classes share methods via the prototype.
**Follow-ups:** (1) Cost at 100 000 instances? (2) Make methods shared while keeping privacy. *(WeakMap/`#private`, Extension.)*

### F4 · Closures/Function factory · Easy · Core
**Problem solved:** Generate specialised functions from one general function.
```js
const makeRateLimiter = max => { let n = 0; return () => n++ < max; };
const allowFive = makeRateLimiter(5);
```
**When:** configuration captured once, reused many times. **Trade-offs:** each product holds its own environment; over-factory-ing hurts readability.
**Follow-ups:** (1) Independent state per product? *(Yes.)* (2) Factory vs partial application.

### F5 · HOF/Decorator (wrapper) · Intermediate · Core
**Problem solved:** Add cross-cutting behaviour (logging, timing, retry, once) without changing the target.
```js
const decorate = (fn, before, after) => function (...args) {
  before(args);
  const r = fn.apply(this, args);
  after(r);
  return r;
};
```
**When:** behaviour orthogonal to the core function. **Trade-offs:** changes `name`/`length`; stacks make debugging harder; async functions need promise-aware wrappers; order of stacked decorators matters.
**Follow-ups:** (1) Must forward what? *(this, args, return, errors.)* (2) Order: `log(retry(fn))` vs `retry(log(fn))`.

### F6 · Closures/Memoization · Advanced · Core
**Problem solved:** Avoid recomputing pure results.
```js
const memo = fn => { const c = new Map(); return a => c.has(a) ? c.get(a) : (c.set(a, fn(a)), c.get(a)); };
```
**When:** pure, deterministic, repeatedly called, costly. **Trade-offs:** unbounded memory, key serialisation cost, stale data for impure functions, defeats GC for object keys (use `WeakMap`).
**Practical example:** formatters, selectors (E9).
**Follow-ups:** (1) Memoize a recursive function correctly. (2) Methods: why must `this` be part of the key (G4)?

### F7 · Composition/Middleware chain · Advanced · Core
**Problem solved:** Pluggable steps around a core handler, each deciding whether to call `next`.
```js
const apply = (handler, ...mws) => mws.reduceRight((next, mw) => mw(next), handler);
```
**When:** request pipelines, logging/auth/error layers. **Trade-offs:** order-sensitive; harder tracing; a missing `next` silently ends the chain; each layer adds a call frame.
**Follow-ups:** (1) Where should error handling live? *(Outermost.)* (2) What if middleware must run code *after* `next` even when it throws? *(`try/finally`, G14.)*

### F8 · Currying/Partial application as abstraction · Intermediate · Core
**Problem solved:** Reuse a general function with some arguments fixed, in data-last style.
```js
const prop = key => obj => obj[key];
const getName = prop("name");
```
**When:** building small reusable pieces for pipelines and callbacks. **Trade-offs:** extra closures, argument-order discipline (configuration first, data last), poor fit for variadic/optional args (A34).
**Follow-ups:** (1) Why data-last? (2) Partial vs curry for a 4-arg function.

### F9 · Composition/Pipelines · Intermediate · Core
**Problem solved:** Express a transformation as a readable sequence of small pure steps.
```js
const normalise = pipe(trim, toLower, collapseSpaces);
```
**When:** data cleaning, formatting, derivation. **Trade-offs:** unary-stage constraint; debugging (use a `tap` stage); error context (G11); allocations per stage.
**Follow-ups:** (1) Add a `tap(fn)` for logging. (2) Branching inside a pipe?

### F10 · Composition/Predicate combinators · Intermediate · Core
**Problem solved:** Build complex conditions from small named predicates.
```js
const isAdult = u => u.age >= 18, isActive = u => u.active;
const canVote = and(isAdult, isActive);       // `and` from C20
```
**When:** filtering, validation, permissions. **Trade-offs:** all predicates see the *same* input (not pipe); short-circuit evaluation order; truthy values returned by predicates.
**Follow-ups:** (1) Why isn't this `pipe`? (2) Add `none`/`some` semantics.

# SECTION G — Complex SDE2 scenarios (15)

Each combines multiple topics. Verified ✅ where run in Node.

### G1 · this + HOF · Detached method through `map` · Advanced · Core
**Problem:** `const api = { base: "/v1", url(p) { return this.base + p; } };` then `["/a","/b"].map(api.url)`.
**Reasoning:** `api.url` is detached and `map` calls it plainly → `this = globalThis` → `["undefined/a","undefined/b"]` ✅ (strict: TypeError).
**Solution:** `map(p => api.url(p))`, `map(api.url, api)` (thisArg) or `map(api.url.bind(api))` ✅.
**Trade-offs:** wrapper keeps late binding of `api.url`; `bind` freezes now; `thisArg` only works for APIs that offer it.
**Edge cases:** `map` also passes `(index, array)`, so extra args reach `url`.
**Follow-ups:** (1) Decorate `api.url` with a logging HOF; does the fix still work? (2) Make `api` immune using a closure factory. (3) What if `url` were an arrow?

### G2 · new + bind · Bound constructor with pre-filled args · Advanced · Core
**Problem:** `function Point(x, y){ this.x = x; this.y = y; } const AtOrigin = Point.bind({ignored:true}, 0); const p = new AtOrigin(5);`
**Reasoning:** `new` ignores the bound `this`, constructs `Point`, **prepends** `0` → `p = {x:0, y:5}`, `p instanceof Point` and `instanceof AtOrigin` are `true` ✅.
**The trap:** a *naive* `myBind` (C12) under `new` returns an **empty wrapper instance** (`{}`), `instanceof Point` is `false`, and it **pollutes the bound thisArg** with `x:0,y:5` ✅.
**Solution:** C13 (`new.target` + `Reflect.construct`).
**Trade-offs:** native handles `name`/`length`/`instanceof` correctly; hand-rolled never fully.
**Follow-ups:** (1) Why is the pollution bug nasty? (2) Does `new` + bound *arrow* work? *(TypeError.)* (3) Bound `class`.

### G3 · Decorator + this · Decorated method · Advanced · Core
**Problem:** Wrap `acct.withdraw` with `logged = fn => function(...a){ console.log("→", fn.name); return fn.apply(this, a); }`; then `const w = acct.withdraw; w(5)`.
**Reasoning:** Called as `acct.withdraw(5)` the wrapper's `this` is `acct` and is forwarded ✅. Detached `w(5)` loses `this` again: the decorator can't fix a lost receiver.
**Solution:** forward `this`; bind at the injection point when handing methods out.
**Trade-offs:** decorating on a shared prototype affects all instances; per-instance wrapping costs memory.
**Edge cases:** `fn.name` is inferred (`"withdraw"`), but the wrapper's own `name` is `""`.
**Follow-ups:** (1) Apply to every method of an object. (2) Preserve `name`/`length`. (3) Async methods.

### G4 · Memoize + closures · Cache bug on prototype methods · Advanced · Core
**Problem:** `Person.prototype.full = memoize(function(){ return this.f + " " + this.l; })` with `memoize` keyed by `JSON.stringify(args)`.
**Reasoning:** No arguments → key `"[]"` for **every** instance → `p1.full()` and `p2.full()` both return `"A B"` ✅.
**Solution:** key by receiver: `WeakMap<this, Map<argsKey, result>>`; instances keep independent caches and become collectable ✅ (`"A B"`, `"C D"`).
**Trade-offs:** per-instance memory vs correctness; `WeakMap` avoids leaks.
**Edge cases:** mutable instance fields invalidate caches; non-object receivers (`this` undefined) can't be WeakMap keys.
**Follow-ups:** (1) How would invalidation work? (2) Why is a shared closure cache correct for pure standalone functions? (3) `Map` instead of `WeakMap` consequences.

### G5 · Currying + this · Where does `this` come from? · Advanced · Core
**Problem:** `o.cg = curry(o.greet); o.cg("1","2")` vs `const s = o.cg("1"); s("2")`.
**Reasoning:** With C15's `this`-forwarding, a **single** call `o.cg("1","2")` works (`"o12"`) ✅. In the **stepwise** form the returned function is invoked *plain* (`s("2")`), so `this` is lost (`"LOST"`/`undefined12`) ✅. `this` is bound only at the call that actually executes the target, with that call's receiver.
**Solution:** `curry(o.greet.bind(o))` ✅, or avoid `this` in curried functions.
**Trade-offs:** `bind` locks the receiver; closure-based design avoids the issue.
**Follow-ups:** (1) Why can't a curry helper "remember" the first receiver? *(It could, but that diverges from native semantics.)* (2) Which receiver wins if steps are called on different objects?

### G6 · Pipeline order · Wrong transformation order · Advanced · Core
**Problem:** Price pipeline: flat discount `−10`, tax `×1.18`, round to 2dp. Input `100`.
**Reasoning:** `pipe(discount, tax, round)(100)` → `106.2`; `pipe(tax, discount, round)(100)` → `108` ✅. Multiplicative stages commute; **additive-after-multiplicative stages do not**. Using `compose(discount, tax, round)` by habit silently reverses the order.
**Solution:** name stages, add tests with non-commutative values, prefer `pipe` for readability.
**Trade-offs:** rounding per stage vs at the end changes totals (money: integers/cents).
**Follow-ups:** (1) Write a test that detects wrong order. (2) Where should rounding live? (3) How does `compose` vs `pipe` naming cause production bugs?

### G7 · Closures · Shared mutable state escapes · Advanced · Core
**Problem:** `createCart()` returns `getItems: () => items` and `add(item){ items.push(item) }`.
**Reasoning:** Callers get the **live array** (`cart.getItems().push(x)` bypasses validation) and aliased item objects can be mutated later; the closure's privacy only protects the *binding*, not the object it references.
**Solution:** return copies (`items.slice()`), freeze/clone items on entry, expose operations not data.
**Trade-offs:** copy cost O(n) per read; deep-clone cost; immutability libraries.
**Edge cases:** shallow vs deep copy; `Object.freeze` shallow.
**Follow-ups:** (1) Defensive copy on input too? (2) `Object.freeze` limits. (3) Is a getter returning a copy "private enough"?

### G8 · Callbacks + GC · Reusable callback registry retains memory · Advanced · Core
**Problem:** `onChange(listener)` pushes listeners into a module-level array; listeners close over component data; nothing unsubscribes.
**Reasoning:** The registry keeps listeners reachable → their captured environments stay reachable. Also, unbounded memoize caches behave identically.
**Solution:** `subscribe` returns `unsubscribe` (C23), cap/evict caches (LRU), `WeakMap`/`WeakRef` where semantics allow, avoid capturing large objects (compute needed values first).
**Trade-offs:** `WeakRef`/finalisation timing is non-deterministic; don't build correctness on it.
**Follow-ups:** (1) How would you detect it? *(heap snapshots comparison.)* (2) What does the V8 shared-context behaviour add? (3) Registry `once` semantics.

### G9 · Currying + arity · A curried function reports `length` 0 · Advanced · Core
**Problem:** `const c = curry((a,b,c) => a+b+c)`; then `c.length`, and passing `c` to another arity-reading utility (e.g. `curry(c)`, `partial`, `bind`-based helpers).
**Reasoning:** `curried(...args)` is a rest-parameter function → `c.length === 0` ✅. Any utility trusting `.length` misreads it (e.g. `curry(c)` fires immediately).
**Solution:** define arity explicitly (`curryN`), or set `length` via `Object.defineProperty(curried, "length", { value: n - args.length })`.
**Trade-offs:** explicit arity is robust but verbose; patching `length` is non-obvious.
**Follow-ups:** (1) What's `bound.length` of a bound curried function? (2) Do libraries expose `length` correctly? (3) Add placeholder support.

### G10 · Function factory + curry · Configurable validators · Advanced · Core
**Problem:** Design `between(min)(max)(value)`, usable standalone and inside `and(...)`.
```js
const between = min => max => {
  if (min > max) throw new RangeError("min > max");
  return v => v >= min && v <= max;
};
const valid = and(between(1)(10), v => v % 2 === 0);
```
**Reasoning:** Config-first, data-last makes factories pipeline-friendly; validate configuration **at construction**, not on every call.
**Trade-offs:** curried calls create objects; error location is the factory call; flexible curry would allow `between(1, 10)`.
**Edge cases:** `NaN`, non-numbers, inclusive vs exclusive bounds.
**Follow-ups:** (1) Add error messages. (2) Compare with a config object. (3) Memoize factories?

### G11 · Pipeline debugging · Stage returns `undefined` · Advanced · Core
**Problem:** `pipe(parse, pick)('{"a":1}')` throws `Cannot read properties of undefined (reading 'name')`: with no hint which stage failed.
**Reasoning:** A stage returned/received `undefined`, and the next stage crashed. Errors lack context.
**Solution:** wrap each stage with context:
```js
const pipeCtx = (...fns) => x => fns.reduce((acc, fn, i) => {
  try { return fn(acc); }
  catch (e) { e.message = `stage ${i} (${fn.name || "anonymous"}): ` + e.message; throw e; }
}, x);
// "stage 1 (pick): Cannot read properties of undefined (reading 'name')" ✅
```
**Trade-offs:** try/catch per stage (cost small); `Result` types make failures explicit.
**Follow-ups:** (1) Add a `tap` stage. (2) Early exit on `null`. (3) Async stages.

### G12 · Callbacks · Sometimes-sync, sometimes-async API · Advanced · Extension
**Problem:** `function get(cache, cb){ if (cache) cb("cached"); else setTimeout(() => cb("fetched"), 0); }`
**Reasoning:** With a cache hit, the callback runs **before** the line after `get(...)` ✅ (order `A, after-A`); on a miss it runs after. Callers can't reason about ordering, a classic source of bugs.
**Solution:** be consistently async (`queueMicrotask(() => cb(...))` / `setTimeout`), or consistently sync; promises always resolve handlers asynchronously.
**Trade-offs:** consistent async costs a tick; sync is simpler but must be documented.
**Follow-ups:** (1) Why is "released Zalgo" the name? (2) Fix with promises. (3) Impact on tests.

### G13 · HOF + arity · `map(parseInt)` and callback signatures · Advanced · Core
**Problem:** `["1","2","3"].map(parseInt)`.
**Reasoning:** `map` passes `(value, index, array)`; `parseInt(value, radix)` uses the index as radix → `[1, NaN, NaN]` ✅.
**Solution:** `map(Number)`, `map(x => parseInt(x, 10))`, or `const unary = fn => x => fn(x)`.
**Trade-offs:** `unary` restores contract; variadic callbacks are fragile; TypeScript catches some.
**Edge cases:** any callback with optional trailing parameters is vulnerable to the extra `index`/`array` arguments that `map`, `filter` and `forEach` pass.
**Follow-ups:** (1) Why does a curried function passed to `map` misbehave? (2) Which built-ins are arity-sensitive? (3) Write `unary` and `nAry`.

### G14 · Middleware · Order, short-circuit and cleanup · Advanced · Core
**Problem:** Chain `[errorHandler, logger, auth]` around a handler that throws.
**Reasoning ✅:** unauthenticated → auth short-circuits (`401`), logger logs `>log, auth-denied, <log`. Authenticated + handler throws → error handler returns `500`, but the log shows `>log, caught` with **no `<log`** because the logger has no `try/finally`.
**Solution:** wrap post-`next` logic in `try/finally`; put error handling outermost; document order.
**Trade-offs:** ordering is implicit; each layer adds stack depth; async needs awaiting `next`.
**Follow-ups:** (1) Where should auth go relative to logging? (2) Let middleware add data to `ctx` safely. (3) Async version.

### G15 · Closures vs alternatives · Private state design · Advanced · Core
**Problem:** Implement a `User` with a private password hash for many instances; compare approaches.
| Approach | Privacy | Memory | Notes |
|---|---|---|---|
| Closure factory | true (unreachable) | methods per instance | no `instanceof`, no prototype sharing |
| `WeakMap` keyed by instance | module-level privacy | shared methods | boilerplate |
| `class` with `#private` (Extension) | language-enforced | shared methods | needs classes; not accessible via reflection |
| `_name` convention | none | shared methods | by convention only |

**Reasoning:** Choose by instance count, need for inheritance/`instanceof`, and testability.
**Follow-ups:** (1) How do you unit-test private state? *(Through behaviour.)* (2) Serialisation (`JSON.stringify`) behaviour of each approach. (3) Closure memory at 100 000 instances.
