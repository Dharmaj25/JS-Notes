# Closures

---

## Before Closures — The Foundation

You already know everything that makes closures possible:

```
Lexical scope       → a function's scope is set at write time
Scope chain         → inner scopes can access outer variables
Execution context   → every function call gets its own EC
Lexical environment → each EC has an environment record + outer reference
First-class fns     → functions can be returned from other functions
```

Closures are not a new mechanism. They are the natural result of these things working together.

---

## What is a Closure?

When a function is defined inside another function, the inner function has access to the outer function's variables — even after the outer function has returned and its execution context has been popped off the call stack.

The inner function **closes over** those variables. That's a closure.

> **A closure is a function that remembers the variables from the scope where it was created — even after that scope no longer exists.**

```js
function outer() {
  let count = 0; // outer variable

  function inner() {
    count++;           // inner accessing outer's variable
    console.log(count);
  }

  return inner; // returning the inner function
}

const counter = outer(); // outer() runs and returns inner
                          // outer's EC is popped off the stack
                          // but count is NOT garbage collected

counter(); // 1 — count still accessible
counter(); // 2 — same count, still alive
counter(); // 3
```

`outer()` has finished executing. Its EC is gone. But `count` is still alive — because `counter` (the returned `inner` function) holds a reference to the lexical environment where `count` lives.

GC cannot collect `count` because it's still reachable through `counter`.

---

## How Closures Work Under the Hood

You know Lexical Environments from Week 1. Now closures make complete sense.

When `inner` is created inside `outer`:

```
inner's Lexical Environment:
  Environment Record: {}  (inner's own variables)
  Outer Reference: → outer's Lexical Environment
                        ↓
                   { count: 0 }
```

When `outer()` returns `inner`:
- `outer`'s EC is popped off the call stack
- Normally `outer`'s Lexical Environment would be garbage collected
- But `inner` still holds an outer reference to it
- So `outer`'s Lexical Environment stays alive in heap memory

```
HEAP MEMORY (after outer() returns):
┌────────────────────────────────────────────┐
│  outer's Lexical Environment               │
│  { count: 0 }    ← still alive             │
│  kept alive because inner references it   │
└────────────────────────────────────────────┘
         ▲
         │ outer reference
         │
┌────────────────────────────────────────────┐
│  inner function object                     │
│  (assigned to 'counter')                   │
└────────────────────────────────────────────┘
```

When `counter()` is called, `inner` runs and walks up its scope chain — finds `count` in `outer`'s preserved Lexical Environment.

## Lexical Capture — What Gets Captured

The closure captures the **variable itself** — not the value at the time of creation.

This is critical. It's the source of the most famous closure bug.

```js
function outer() {
  let x = 10;

  return function() {
    console.log(x);
  };
}

const fn = outer();
fn(); // 10
```

Simple. Now watch what happens when the variable changes after the closure is created:

```js
function outer() {
  let x = 10;

  const fn = function() {
    console.log(x); // captures the VARIABLE x, not the value 10
  };

  x = 99; // variable changed after closure created

  return fn;
}

const fn = outer();
fn(); // 99 — not 10!
```

The closure captured `x` — the variable. When `x` changes to `99`, the closure sees `99`. It doesn't freeze the value at creation time. It holds a live reference to the variable.

## The Classic Closure Bug — for Loop with var

You saw this in Week 1. Now you understand exactly why it happens.

```js
for (var i = 0; i < 3; i++) {
  setTimeout(function() {
    console.log(i); // all three closures capture the SAME i
  }, 1000);
}
// prints: 3, 3, 3
```

Why?
- `var i` is function-scoped — ONE shared variable
- All three callbacks close over the SAME `i`
- By the time they fire, the loop is done and `i = 3`
- All three read `3`

Fix with `let`:
```js
for (let i = 0; i < 3; i++) {
  setTimeout(function() {
    console.log(i); // each iteration has its OWN i
  }, 1000);
}
// prints: 0, 1, 2
```

`let` creates a new `i` binding per iteration. Each callback closes over its own independent `i`.

Fix with IIFE (before `let` existed):
```js
for (var i = 0; i < 3; i++) {
  (function(j) {
    setTimeout(function() {
      console.log(j); // closes over j — a new variable per call
    }, 1000);
  })(i);
}
// prints: 0, 1, 2
```

Each IIFE call creates a new scope with its own `j`. Each callback closes over a different `j`.

## Private State — One of the Most Important Use Cases

Closures are the primary way to create truly private variables in JS.

Without closures, there's no built-in way to hide data:

```js
// No privacy — count is exposed
let count = 0;

function increment() { count++; }
function getCount() { return count; }

count = 999; // anyone can directly modify it ❌
```

With closures, `count` is hidden inside the outer function's scope:

```js
function createCounter() {
  let count = 0; // private — not accessible from outside

  return {
    increment: function() { count++; },
    decrement: function() { count--; },
    getCount:  function() { return count; }
  };
}

const counter = createCounter();

counter.increment();
counter.increment();
counter.decrement();
console.log(counter.getCount()); // 1

console.log(counter.count); // undefined — cannot access directly ✅
counter.count = 999;         // this creates a NEW property on the object
                              // does NOT affect the private count ✅
console.log(counter.getCount()); // still 1 — private count untouched
```

`count` lives in `createCounter`'s lexical environment. The returned object's methods close over it. Nothing outside can touch it directly — only through the provided interface.

This is the **module pattern** — creating a public interface over private state.

## Multiple Closures Over the Same Variable

When multiple functions close over the same variable, they all share it:

```js
function createCounter() {
  let count = 0;

  const increment = function() { count++; };
  const decrement = function() { count--; };
  const getCount  = function() { return count; };

  return { increment, decrement, getCount };
}

const counter = createCounter();

counter.increment(); // count = 1
counter.increment(); // count = 2
counter.decrement(); // count = 1
console.log(counter.getCount()); // 1
```

All three functions close over the SAME `count` variable. They share state. Calling `increment` affects what `getCount` returns.

---

## Each Closure Call Gets Its Own Scope

When you call the outer function multiple times, each call creates a completely independent closure:

```js
function createCounter() {
  let count = 0;
  return function() {
    count++;
    return count;
  };
}

const counter1 = createCounter();
const counter2 = createCounter();

console.log(counter1()); // 1
console.log(counter1()); // 2
console.log(counter1()); // 3

console.log(counter2()); // 1 — completely independent
console.log(counter2()); // 2

console.log(counter1()); // 4 — counter1 unaffected by counter2
```

`counter1` and `counter2` each have their own `count`. They don't share state. Each call to `createCounter()` creates a new lexical environment with a new `count`.

## Closure Use Cases

### 1. Data Privacy / Module Pattern

Already shown above. Creating private state with a public interface.

```js
function createBankAccount(initialBalance) {
  let balance = initialBalance; // private

  return {
    deposit:    function(amount) { balance += amount; },
    withdraw:   function(amount) {
      if (amount > balance) {
        console.log("Insufficient funds");
        return;
      }
      balance -= amount;
    },
    getBalance: function() { return balance; }
  };
}

const account = createBankAccount(100);
account.deposit(50);
account.withdraw(30);
console.log(account.getBalance()); // 120
console.log(account.balance);      // undefined — private ✅
```

### 2. Function Factories

Creating customized functions:

```js
function makeMultiplier(factor) {
  return function(number) {
    return number * factor; // closes over factor
  };
}

const double = makeMultiplier(2);
const triple = makeMultiplier(3);
const tenX   = makeMultiplier(10);

double(5);  // 10
triple(5);  // 15
tenX(5);    // 50
```

Each returned function remembers its own `factor`.

### 3. Memoization — Caching Expensive Results

```js
function memoize(fn) {
  const cache = {}; // private cache — closes over it

  return function(n) {
    if (cache[n] !== undefined) {
      console.log("from cache");
      return cache[n];
    }
    cache[n] = fn(n);
    return cache[n];
  };
}

function slowSquare(n) {
  // imagine this is expensive
  return n * n;
}

const fastSquare = memoize(slowSquare);

fastSquare(5); // computes: 25
fastSquare(5); // from cache: 25
fastSquare(6); // computes: 36
fastSquare(6); // from cache: 36
```

`cache` is private to `memoize`. The returned function closes over it and builds it up over calls.

### 4. Event Handlers with State

```js
function makeClickHandler(buttonName) {
  let clickCount = 0; // private per button

  return function() {
    clickCount++;
    console.log(buttonName + " clicked " + clickCount + " times");
  };
}

const handleLoginClick  = makeClickHandler("Login");
const handleSignupClick = makeClickHandler("Signup");

handleLoginClick();  // "Login clicked 1 times"
handleLoginClick();  // "Login clicked 2 times"
handleSignupClick(); // "Signup clicked 1 times" — independent state
```

### 5. Partial Application

Pre-filling some arguments of a function:

```js
function multiply(a, b) {
  return a * b;
}

function partial(fn, firstArg) {
  return function(secondArg) {
    return fn(firstArg, secondArg); // closes over firstArg
  };
}

const double = partial(multiply, 2);
const triple = partial(multiply, 3);

double(5); // 10
triple(5); // 15
```

The returned function remembers `firstArg` and `fn` from the outer scope. Currying and partial application (Saturday) are built entirely on closures.

## What Closures Are NOT

Common misconceptions:

```
Closures are NOT:
  ❌ Only about returning functions
     → A closure exists any time an inner function
       accesses an outer variable — even without returning

  ❌ A copy of the outer scope
     → Closures capture the VARIABLE, not the value
     → Changes to the variable are visible in the closure

  ❌ Specific to arrow functions
     → Regular functions create closures too
     → Any function that accesses outer scope variables

  ❌ Automatically a performance problem
     → Only a problem if closures prevent GC of large data
     → Used correctly they're fine
```

## Closures and Memory — The Connection to Week 1

You know from Week 1 that GC frees memory when objects become unreachable.

Closures keep lexical environments alive:

```js
function createHeavyClosure() {
  const largeData = new Array(1000000).fill("data"); // large

  return function() {
    console.log(largeData.length); // closes over largeData
  };
}

const fn = createHeavyClosure();
// largeData is still in memory — fn holds a reference to it

fn();    // 1000000
fn = null; // release the closure
           // now largeData becomes unreachable → GC collects it ✅
```

When you're done with a closure, release the reference so GC can clean up the captured variables.

---

## How Everything Connects

```
Lexical scope
  → inner functions can access outer variables
  → scope is determined at write time

Execution context + Lexical environment
  → each function call creates its own LE
  → inner function's outer reference points to outer's LE

First-class functions
  → inner function can be returned
  → returned function carries its outer reference with it

Garbage collection
  → outer LE stays alive as long as inner function references it
  → releasing the closure = outer LE becomes collectible

All of this together = CLOSURE
  → a function that remembers the scope it was born in
  → even after that scope's EC is gone from the call stack
```

## What Interviewers Test

**1. Define closure precisely**
Not just "a function inside a function". The correct definition: a function that remembers the variables from the scope where it was created, even after that scope's execution context is gone.

**2. Closures capture variables, not values**
The most common gotcha. If the variable changes after the closure is created, the closure sees the new value. This explains the for loop bug.

**3. The for loop closure bug — with var AND the fix**
Know why it happens (one shared var), know both fixes (let creates new binding per iteration, IIFE creates new scope per iteration).

**4. Private state with closures**
The module pattern. Know that direct property assignment on the returned object does NOT affect the private variable.

**5. Each outer call = independent closure**
`createCounter()` called twice = two independent `count` variables. They don't share state.

**6. Connect closures to GC**
Closures keep lexical environments alive. Set closure references to null when done — especially if they capture large data.

**7. Real use cases**
Private state, function factories, memoization, event handlers with state, partial application. Know at least 3 with code.

## Mental Models

**Closure = a function with a backpack.**
When the inner function is returned, it packs up the variables it needs from the outer scope and carries them wherever it goes. The backpack stays with the function forever.

**Lexical environment = the room where the function was born.**
When the function leaves the room (is returned), it keeps a key to that room. Even after everyone else has left, it can still go back in and read what's there.

**Private state = a safe with a combination lock.**
The variable is the contents. The closure is the lock. The methods are the only keys. Nobody else can get in.

**Closure captures the variable, not the value.**
It's holding the address of the variable's home — not a photo of what was inside at one moment. If someone redecorates the home, the closure sees the new decor.

**Each outer call = a new room.**
Calling `createCounter()` twice creates two separate rooms with two separate counters inside. Changes in one room don't affect the other.
